# ТЗ: развитие ядра AEGIS до полного контура «модель мира → прогноз → решение → опыт → эволюция → открытие»

Документ реализует целиком текст `развитие.txt`. Версия ядра-основания: коммит
`0c72a51` (ветка `close-behaviour-loop`).

**Режим исполнения — максимальный.** Никаких заглушек, `TODO`,
`NotImplementedError`, «пока упрощённо», «в следующей версии». Каждый модуль
сдаётся целиком: алгоритм, персистентность, интеграция в тик, конфиг, API,
дашборд, тесты, документация. Любая функция, которую нельзя сдать полностью,
исключается из ТЗ, а не сдаётся наполовину.

### 1.2. Разрывы относительно `развитие.txt`

| № | Требование текста развития | Что есть | Разрыв (что делать) |
|---|---|---|---|
| 1 | «модель мира → **прогноз** → решение» | `WorldModel` — частотная таблица `причина→следствие` со сглаживанием Лапласа. Читается один раз за тик: штраф уверенности за известные провалы | **Нет прогноза как объекта.** Нет состояния мира, нет предсказания следующего состояния/награды, нет ошибки предсказания, нет калибровки, нет планирования по симуляции. Нужен предиктивный WM + планировщик |
| 2 | «обучение через опыт: действие→результат→оценка→новое знание→**изменение поведения**» | `FeedbackLoop` пишет структурированный опыт; он идёт в датасет LoRA и в `WorldModel` | Знание меняет поведение только через один канал (штраф уверенности). Нет явной **политики поведения**, обучаемой из опыта, нет правил с доказательной базой, нет измерения «насколько опыт изменил решения» |
| 3 | «DeepSeek-R1-Distill-Qwen-1.5B слишком маленький, возьми Kimi K3» | `LOCAL_MODEL_PATH` жёстко указывает на 1.5B; два провайдера (DeepSeek/Claude) захардкожены в `llm.py`, парсинг JSON ручной | Нужен провайдер-агностичный роутер («кора») с ролями, схемной валидацией, кэшем, failover; Kimi — первоклассный провайдер |
| 4 | «цель → ценность → **приоритет** → **ресурс** → действие» | `GoalEngine` (цель) + `GoalIntelligence` (ценность) | **Нет приоритезации как отдельного шага и нет экономики ресурсов.** Действия выполняются по расписанию `tick % N`, а не по бюджету. Токены/время/процессы никем не выделяются под цель |
| 5 | «создать **10 вариантов** улучшения → проверить → оставить лучший» | `EvolutionEngine` — **один** кандидат за раз, мутация одного параметра round-robin, оценка на общем бенчмарке | Нужна **популяционная** эволюция: 10 вариантов за поколение, изолированная параллельная оценка, отбор, элитизм, архив новизны, train/valid/test-сплит против переобучения. Плюс: текущий геном (`learning_rate`, `dropout`, `attention_heads`…) **почти не влияет** на измеряемую метрику — геном надо заменить на реально действующие параметры |
| 6 | «поверх ядра поставить Kimi K3/DeepSeek/GPT как кору мозга» | LLM вызывается из 8 мест `substrate.py` напрямую | Нужен слой `Cortex` с ролями (planner/proposer/critic/judge/coder), политикой стоимости и деградацией до детерминированного пути |
| 7 | «улучшение алгоритмов мышления: найти слабость → новые алгоритмы рассуждения → проверить → оставить» | Нет ничего. `_skill_synthesis` синтезирует **навыки** (`solve(payload)`), а не **стратегии рассуждения** | Нужен реестр стратегий рассуждения, интерпретатор DSL, детектор слабостей, синтезатор стратегий, арена с held-out приёмкой |
| 8 | «создание новых знаний: данные → гипотеза → **математическая модель** → эксперимент → открытие» | Нет ничего. `external_learning` только скачивает тексты | Нужен Discovery Engine: пул данных, генерация гипотез с контролем множественных сравнений, символьная регрессия, предрегистрация, интервенционные самоэксперименты, статистика, реестр открытий |

### 1.3. Технические долги, которые ТЗ обязано закрыть попутно

1. `Substrate` — «божественный объект» на 1763 строки; после добавления 7 систем станет неуправляемым. **Требуется декомпозиция на фазовые оркестраторы** (см. §3.9), при полном сохранении внешнего поведения и API.
2. Расписание всей активности — арифметика `tick % N` в 14 местах. **Заменяется на планировщик задач с бюджетами** (§M4).
3. `llm._parse_json_response` — ручной парс без схемы; модель, вернувшая «почти правильный» JSON, молча роняет фазу. **Заменяется на схемную валидацию с ремонтом** (§M8).
4. Метрики живут только в `full_status()` и не имеют истории. **Требуется телеметрия-таймсерия** (§M9) — без неё Discovery Engine нечего анализировать.
5. `time.time()` вызывается напрямую в 20+ модулях — тесты на временные окна нестабильны. **Вводятся инъектируемые часы** (§3.6).
6. Конфигурация локальной модели рассчитана на одну конкретную модель:
   `LORA_TARGET_MODULES` захардкожен (`config.py:129`), `LOCAL_MODEL_DTYPE` по
   умолчанию `float32` (двойной расход памяти), `LOCAL_MODEL_MAX_LENGTH=2048`,
   отсутствует проверка «модель против доступной памяти» и проверка, что LoRA
   нашла хотя бы один целевой модуль. **Исправляется в M8.3a–M8.3c.**

## Часть III. Общесистемные требования

### 3.1. Детерминизм (обязательно)
- `random`, `numpy.random`, `secrets` **запрещены** во всём пакете `aegis`, кроме
  явно помеченного модуля криптографии (его нет). Тест `test_zero_randomness.py`
  расширяется на новые модули и на импорт-граф.
- Где нужна «случайность» (мутации, бутстрап, выбор точек эксперимента) —
  используются детерминированные последовательности низкой дискрепантности
  (Halton/Sobol, собственная реализация в `aegis/util/quasirandom.py`) либо
  хеш-индексирование (`blake2b(seed_material)`), полностью воспроизводимые.
- Порядок обхода любых `dict`/`set`, попадающий в результат, сортируется.
- Приёмка: запуск 300 тиков дважды из одного состояния даёт **побитово
  одинаковый** хеш состояния (`substrate.state_digest()`), тест
  `tests/test_determinism_e2e.py`.

### 3.2. Персистентность
- Все новые хранилища — атомарная запись (`tmp` + `replace`), поле
  `"schema_version": int` в корне, реестр миграций `aegis/store/migrations.py`
  с функцией `migrate(data, from_v, to_v)`; неизвестная будущая версия →
  хранилище не читается, пишется предупреждение, работа продолжается с пустым
  состоянием (никогда — падение).
- Каждое хранилище обязано иметь верхнюю границу размера и правило вытеснения,
  основанное на **информативности**, а не только на давности (как уже сделано в
  `WorldModel._retention_score`).
- Битая строка JSONL пропускается, остальные читаются (правило уже действует в
  `FeedbackLoop._load`).

### 3.3. Безопасность
- Ни одна новая система **не может обойти** `EthicsCore.evaluate_action` и
  `SelfPreservation.is_modification_safe`.
- Множество **неприкосновенных параметров** `IMMUTABLE_PARAMS` (этические
  пороги, лимиты kill switch, границы ресурсов безопасности, размеры
  предохранителей) — эволюция, политика поведения и самоэксперименты не имеют к
  ним доступа; попытка изменения = блокировка + запись в автобиографию + метрика.
- Интервенционные самоэксперименты (M7) требуют: параметр в белом списке,
  амплитуда ≤ заданной, откат по таймеру, немедленный откат при `health=critical`
  или срабатывании kill switch.
- Всё исполнение сгенерированного кода — только через существующий sandbox
  (`aegis/eval/sandbox.py`, `python -I` + AST-гейт). DSL стратегий рассуждения
  (M6) **не является** исполняемым Python: интерпретируется собственным
  интерпретатором с фиксированным набором операций.
- Правка исходников остаётся opt-in и выключенной по умолчанию.

### 3.4. Производительность
- Бюджет фазы без LLM: PERCEIVE ≤ 5 мс, EVALUATE ≤ 10 мс, DECIDE ≤ 30 мс,
  ACT (без внешних вызовов) ≤ 20 мс, REFLECT ≤ 15 мс — измеряется тестом
  `tests/test_phase_budgets.py` на среднем из 200 тиков.
- Всё тяжёлое (оценка популяции, бенчмарк, обучение, эксперименты) — в пуле
  процессов, отсоединённые задачи, никогда не в теле тика.
- Механизм `regulate_capacity` расширяется на новые структуры (переходы WM,
  правила политики, реестр стратегий, кэш кортекса).

### 3.5. Наблюдаемость
- Каждая система обязана вернуть `status() -> dict` и попасть в `full_status()`.
- Каждая система пишет свои метрики в `Telemetry` (M9) каждые N тиков.
- Каждая система имеет секцию на дашборде и REST-эндпоинт.

### 3.6. Часы
- Новый модуль `aegis/clock.py`: `class Clock: now() -> float; monotonic() -> float`.
  Глобальный экземпляр `CLOCK`, подменяемый в тестах на `FrozenClock`.
- Все **новые** модули используют только `CLOCK`. Существующие переводятся на
  `CLOCK` в рамках этапа 0 (механическая замена `time.time()`), с сохранением
  поведения.

### 3.7. Качество
- Гейт покрытия ветвей — **не ниже 90%** по пакету (сейчас 92%); новые модули
  сдаются с покрытием **≥95%**.
- Мутационный харнесс `scripts/mutation_test.py` пополняется всеми новыми
  модулями; выживший немутационно-эквивалентный мутант = провал сборки.
- BDD-сценарии (`pytest-bdd`) на каждый замкнутый контур: «дано состояние —
  когда произошло — тогда поведение изменилось».
- Тест на утечку данных: ни один текст held-out задачи не должен попадать в
  промпт синтезатора (`tests/test_no_leakage.py`).

### 3.8. Обратная совместимость
- Существующие эндпоинты, ключи `full_status()` и форматы файлов на диске
  сохраняются. Новое добавляется, старое не переименовывается.
- Старые данные читаются миграцией (`schema_version` отсутствует → v1).

### 3.9. Декомпозиция Substrate (этап 0, обязателен до остальных)
`substrate.py` разделяется без изменения поведения:

```
aegis/layers/substrate.py            # класс Substrate: состояние, tick(), run(), status
aegis/layers/phases/perceive.py      # PerceivePhase.run(ctx)
aegis/layers/phases/evaluate.py
aegis/layers/phases/decide.py
aegis/layers/phases/act.py
aegis/layers/phases/reflect.py
aegis/layers/phases/context.py       # TickContext: снимок состояния тика + аккумуляторы
```

`TickContext` — единственный объект, который фазы передают друг другу
(dataclass: `tick`, `state`, `metrics`, `focus`, `decision`, `plan`,
`prediction`, `leases`, `accumulators`). Приёмка этапа 0: **все существующие
тесты зелёные без изменений**, `full_status()` идентичен по ключам, дифф
поведения = 0 (проверяется `test_determinism_e2e` до/после).

## M1. Предиктивная модель мира (`модель мира → прогноз`)

### M1.1. Назначение
Превратить частотную таблицу причин и следствий в **модель, которая
предсказывает** и **знает, насколько она права**. Прогноз становится объектом
первого класса: он записывается до действия, оценивается после, и его ошибка —
обучающий сигнал и источник любопытства.

### M1.2. Файлы
```
aegis/layers/world/__init__.py
aegis/layers/world/state.py          # StateEncoder, StateKey
aegis/layers/world/transition.py     # TransitionModel
aegis/layers/world/outcome.py        # OutcomeModel
aegis/layers/world/prediction.py     # Prediction, PredictionScorer, Calibration
aegis/layers/world/simulate.py       # Simulator (роллауты)
aegis/layers/world_model.py          # PredictiveWorldModel — фасад, включает старый WorldModel
```
Старый класс `WorldModel` сохраняется как `CausalLinks` внутри фасада; публичные
методы `observe/predict/explain/risks_for/build_chain/refine_chain/status`
остаются с той же сигнатурой (обратная совместимость с тестами и дашбордом).

### M1.3. Структуры данных

**Состояние.** Детерминированное дискретное кодирование:
```python
@dataclass(frozen=True)
class StateKey:
    energy: str        # "lo"|"mid"|"hi"           границы 0.33/0.66
    error: str         # "none"|"low"|"high"       границы 0.05/0.20
    mood: str          # из EmotionalSystem.mood
    mode: str          # consciousness.mode
    focus_kind: str    # категория текущей цели: knowledge|competence|coherence|stability|idle
    perf: str          # тренд бенчмарка: "down"|"flat"|"up" по последним 5 точкам
    load: str          # "lo"|"mid"|"hi" по avg_tick_ms / порог
    def key(self) -> str:  # "e=mid|err=low|mo=curious|md=focused|fk=knowledge|pf=up|ld=lo"
```
`StateEncoder.encode(ctx) -> StateKey` — чистая функция от `TickContext`,
без побочных эффектов, без времени. Набор признаков и границы — в конфиге
(`WM_STATE_BINS`), сами границы **входят в геном эволюции** (M5).

**Модель переходов.** Для каждой пары `(state_key, action)` хранится:
```python
{
  "n": int,                                  # число наблюдений
  "next": {state_key: count},                # распределение следующего состояния
  "features": {feature_name: {value: count}},# помаргинальные счётчики (для сглаживания)
  "updated": float,
}
```
Оценка вероятности: аддитивное сглаживание с backoff — если пара `(s,a)`
наблюдалась < `WM_MIN_N` раз, вероятность берётся из маргинала по `a`, затем из
общего приора. Формула:
`P(s'|s,a) = (c(s,a,s') + α·P_backoff(s'|a)) / (n(s,a) + α)`, `α = WM_SMOOTHING`.

**Модель исхода.** Для `(state_key, action)`:
```python
{"n": int, "succ": int, "r_mean": float, "r_m2": float, "cost_mean": float, "updated": float}
```
`r_mean/r_m2` — онлайн-алгоритм Уэлфорда (дисперсия награды = мера
неопределённости). Вероятность успеха — нижняя граница Вильсона при выборе
(пессимизм) и точечная оценка при отчёте.

**Прогноз.**
```python
@dataclass
class Prediction:
    id: str; tick: int; state: str; action: str
    p_success: float; expected_reward: float; reward_sd: float
    predicted_next: list[tuple[str, float]]     # топ-3 следующих состояния
    predicted_effects: list[dict]               # из CausalLinks.predict
    confidence: float                            # f(n, дисперсия, калибровка)
    horizon: int                                 # 1 = следующий тик
```
Прогнозы пишутся в `data/world_model/predictions.jsonl` (ограничен
`WM_MAX_PREDICTIONS`), закрываются в REFLECT.

### M1.4. API
```python
class PredictiveWorldModel:
    # обучение
    def observe(self, cause: str, effect: str, success: bool = True) -> None      # legacy
    def observe_transition(self, s: StateKey, a: str, s_next: StateKey) -> None
    def observe_outcome(self, s: StateKey, a: str, success: bool, reward: float, cost: float) -> None

    # прогноз
    def predict_outcome(self, s: StateKey, a: str) -> OutcomePrediction
    def predict_next(self, s: StateKey, a: str, k: int = 3) -> list[tuple[str, float]]
    def make_prediction(self, s: StateKey, a: str, tick: int) -> Prediction
    def score_prediction(self, pred_id: str, success: bool, reward: float,
                         actual_next: StateKey) -> PredictionScore

    # симуляция
    def rollout(self, s: StateKey, actions: list[str], depth: int) -> RolloutResult
    def best_sequence(self, s: StateKey, actions: list[str], depth: int,
                      beam: int, discount: float) -> list[str]

    # качество модели
    def calibration(self) -> dict     # бины, Brier, ECE, MAE награды, покрытие
    def surprise(self) -> float       # скользящая средняя −log P(факт) за окно
    def knows(self, s: StateKey, a: str) -> float   # 0..1 — насколько модель обучена здесь

    # совместимость
    def predict(self, cause, k=5); def explain(self, effect, k=5)
    def risks_for(self, tokens, k=5); def build_chain(...); def refine_chain(...)
    def status(self) -> dict; def save(self) -> None
```

### M1.5. Алгоритмы
1. **Роллаут** — детерминированный, по математическому ожиданию, без сэмплирования:
   на каждом шаге из состояния `s` для действия `a` берутся топ-`WM_BRANCH`
   следующих состояний с их вероятностями; значение узла
   `V(s,d) = E[r|s,a] − λ·cost − ρ·risk + γ·Σ P(s'|s,a)·V(s',d−1)`,
   листья при `d=0` дают `0`. Ветвление ограничено лучом `beam`; узлы
   мемоизируются по `(state, depth)`. Сложность `O(beam·|A|·depth)`.
2. **Ошибка предсказания**: `brier = (p_success − 1[success])²`;
   `reward_err = |E[r] − r|`; `nll_next = −log P(actual_next)`.
   Экспоненциальное сглаживание всех трёх; ECE считается по 10 бинам.
3. **Surprise → любопытство**: скользящий `nll_next` нормируется и подаётся в
   `GoalEngine.curiosity_level` и в бонус планировщика за исследование
   (`+ β·(1 − knows(s,a))`), что даёт направленное исследование вместо слепого.
4. **Забывание**: переходы стареют экспоненциально (`half-life = WM_HALF_LIFE`
   наблюдений), счётчики умножаются на `0.5^(Δn/H)` при обновлении — модель
   следует за дрейфом системы (после принятой мутации мир буквально меняется).

### M1.6. Интеграция в тик
- **PERCEIVE**: `ctx.state = StateEncoder.encode(ctx)`.
- **EVALUATE**: закрытие прогноза **предыдущего** тика (`score_prediction`),
  обновление калибровки, публикация surprise.
- **DECIDE**: `make_prediction(state, chosen_action)` — прогноз пишется до
  действия, идёт в `Prediction`-лог и в `TickContext`.
- **REFLECT**: `observe_transition`, `observe_outcome` реальными значениями.

### M1.7. Конфиг
`WM_SMOOTHING=1.0`, `WM_MIN_N=3`, `WM_BRANCH=3`, `WM_BEAM=5`, `WM_DEPTH=3`,
`WM_DISCOUNT=0.9`, `WM_HALF_LIFE=500`, `WM_MAX_PREDICTIONS=20000`,
`WM_STATE_BINS` (JSON), `WM_EXPLORE_BONUS=0.15`.

### M1.8. Метрики
`brier`, `ece`, `reward_mae`, `nll_next`, `surprise`, `coverage` (доля тиков, где
`knows(s,a) ≥ 0.5`), `transitions`, `states_seen`, `rollout_ms`.

### M1.9. Критерии приёмки
- После 2000 тиков на стандартной конфигурации: `brier ≤ 0.18`,
  `ECE ≤ 0.08`, `reward_mae ≤ 0.12`; модель строго лучше двух базовых линий —
  «всегда средняя частота успеха» и «всегда 0.5» (проверяется тестом на
  зафиксированном логе).
- Роллаут глубины 3 при `beam=5` укладывается в 15 мс.
- `predict_outcome` для невиданной пары возвращает backoff-оценку, а не ошибку.

### M1.10. Тесты
`test_world_state.py` (кодирование, границы, стабильность), `test_transition_model.py`
(сглаживание, backoff, забывание), `test_outcome_model.py` (Уэлфорд, Вильсон),
`test_prediction_scoring.py` (Brier/ECE/калибровка на синтетике с известным ответом),
`test_simulate.py` (детерминизм, мемоизация, границы), BDD
`features/prediction.feature` — «модель ошиблась → surprise вырос → любопытство выросло».

## M2. Планировщик (`прогноз → решение`)

### M2.1. Назначение
Решение перестаёт быть «взять цель с максимальным `priority·(1−progress)`».
Оно становится результатом сравнения **планов**, оценённых предиктивной моделью
мира, с явным учётом риска, стоимости и ограничений.

### M2.2. Файлы
```
aegis/layers/planner.py       # Planner, Plan, ActionSpace
aegis/layers/actions.py       # реестр действий: имя, аргументы, стоимость, исполнитель
```

### M2.3. Пространство действий
Единый реестр (сейчас действия разбросаны по `_act` как ветки `tick % N`).
**Полный состав — Приложение A**; здесь только форма записи:
```python
@dataclass(frozen=True)
class ActionSpec:
    name: str                       # уникальный идентификатор из Приложения A
    drive: str                      # competence|knowledge|coherence|stability
    cost: ResourceCost              # llm_tokens, wall_ms, subprocess_slots, net_calls, training_slots
    preconditions: tuple[str, ...]  # предикаты над TickContext ("role_deep_available", "energy>0.2")
    executor: str                   # импортируемый путь к исполнителю
    min_interval: int               # минимальный интервал в тиках (rate limit, не триггер)
    reversible: bool
    safety_critical: bool           # иммунитет к подавлению политикой + ресурсный пол
```
`ActionSpace.available(ctx) -> list[ActionSpec]` фильтрует по предусловиям и
`min_interval`; порядок результата — лексикографический по `name`
(детерминизм). Реестр объявляется данными, а не кодом: добавление действия —
одна запись плюс исполнитель, без правки планировщика.

### M2.4. API
```python
@dataclass
class Plan:
    objective: str
    steps: list[str]                # последовательность действий
    expected_value: float
    expected_cost: ResourceCost
    risk: float                     # из WM.risks_for + дисперсии награды
    confidence: float
    rationale: str                  # человекочитаемое обоснование (детерминированное)
    source: str                     # "planner" | "planner+cortex"
    alternatives: list[dict]        # топ-3 отвергнутых с их EV

class Planner:
    def plan(self, ctx: TickContext, objectives: list[str], budget: ResourceBudget) -> Plan
    def evaluate(self, ctx, action_sequence: list[str]) -> float
    def explain(self, plan: Plan) -> str
```

### M2.5. Алгоритм
1. Кандидаты целей: активные цели `GoalEngine` + предложения `MetaGoalGenerator`
   + связанные узлы `CognitiveGraph.related(focus)` + (опционально) предложения
   кортекса.
2. Для каждой цели — набор действий из `ActionSpace.available`.
3. `Planner` вызывает `PredictiveWorldModel.best_sequence` (луч, глубина из
   конфига) и получает `EV`.
4. Скоринг:
   `score = EV·w_ev + value(GoalIntelligence)·w_val + explore_bonus·w_exp
            − cost_norm·w_cost − risk·w_risk + policy_delta(M3)`.
   Все веса — **часть генома эволюции** (M5), а не константы.
5. Фильтр `BehaviourPolicy` (M3): правила могут понизить/заблокировать действие
   в данном состоянии; блокировка требует доказательной базы (§M3.5).
6. `PriorityScheduler` (M4) сортирует по приоритету, `ResourceManager` выдаёт
   аренду; действие без аренды не исполняется, а откладывается.
7. Этика + самосохранение — последний, неотменяемый гейт.
8. `Plan` пишется в `TickContext`, публикуется, логируется в автобиографию при
   `|EV − EV_greedy| > θ` (то есть когда планировщик реально изменил решение).

### M2.6. Роль кортекса
LLM может: (а) предложить дополнительные цели/действия, (б) переранжировать
топ-3 плана с обоснованием. LLM **не может**: обойти политику, ресурсы, этику;
выбрать действие вне реестра `ActionSpace`; изменить веса. Ответ кортекса
валидируется схемой; невалидный ответ игнорируется, путь остаётся
детерминированным.

### M2.7. Метрики
`plans_built`, `planner_override_rate` (доля тиков, где план ≠ жадный выбор),
`ev_realized_gap` (|EV плана − фактическая награда|), `plan_depth`,
`plan_latency_ms`, `blocked_by_policy`, `blocked_by_resources`, `blocked_by_ethics`.

### M2.8. Критерии приёмки
- A/B-харнесс `scripts/ab_planner.py`: 2×2000 тиков (планировщик вкл/выкл на
  одном и том же зафиксированном сценарии среды) даёт прирост средней награды
  **≥10% относительно жадного базиса** при равном бюджете ресурсов.
- `ev_realized_gap` убывает монотонно на окне 1000 тиков (обучаемость).
- Планирование ≤30 мс на тик без LLM.

### M2.9. Тесты
`test_planner.py` (скоринг, детерминизм, порядок гейтов), `test_action_space.py`
(предусловия, стоимость), `test_planner_gates.py` (LLM не может обойти гейт —
мутационно значимый тест), BDD `features/planning.feature`.

## M3. Замыкание «опыт → изменение поведения»

### M3.1. Назначение
Реализовать цепочку `действие → результат → оценка → новое знание → изменение
поведения` так, чтобы последнее звено было **отдельным, наблюдаемым объектом**:
политикой поведения с правилами, у каждого из которых есть доказательная база,
срок жизни и измеренный эффект.

### M3.2. Файлы
```
aegis/layers/policy/__init__.py
aegis/layers/policy/store.py        # PolicyStore: предпочтения (s,a) -> вес
aegis/layers/policy/rules.py        # Rule, RuleMiner, RuleLifecycle
aegis/layers/policy/counterfactual.py # ShadowEvaluator: регрет и эффект политики
```

### M3.3. Предпочтения
`PolicyStore` хранит `pref[(state_key, action)] = {w: float, n: int, updated}`.
Обновление после закрытия опыта:
`w ← w + η·(r − baseline(state)) · (1 − |w|)`, `η = POLICY_LR`, `baseline` —
скользящее среднее награды в этом состоянии (чтобы учить преимущество, а не
абсолютную награду). Границы `w ∈ [−1, 1]`. Вклад в скоринг планировщика —
`policy_delta = w · POLICY_WEIGHT`.

### M3.4. Правила
```python
@dataclass
class Rule:
    id: str
    condition: dict     # {"state": {"error": "high"}, "action": "learn_external"}
    effect: str         # "suppress" | "prefer" | "require_verification"
    support: int        # число наблюдений
    success_rate: float
    wilson_low: float   # нижняя граница 95% доверительного интервала
    status: str         # "candidate" | "active" | "retired" | "refuted"
    created_tick: int; activated_tick: int | None
    measured_effect: float | None   # прирост награды после активации (A/B)
    provenance: list[str]           # id опытов, породивших правило
```

**RuleMiner** (детерминированный, запускается раз в `POLICY_MINE_EVERY_N_TICKS`):
перебирает пары `(подмножество признаков состояния, действие)` до размера
`POLICY_MAX_COND` (по умолчанию 2), считает частоты успеха по журналу опыта,
оставляет кандидатов с `support ≥ POLICY_MIN_SUPPORT` (по умолчанию 20) и
`wilson_low` вне интервала `[base_low, base_high]` базовой частоты (то есть
эффект статистически отличим). Множественные сравнения контролируются
процедурой Бенджамини–Хохберга на всём наборе кандидатов поколения.

### M3.5. Жизненный цикл правила
`candidate → (A/B-проверка) → active → (мониторинг) → retired|refuted`
- Кандидат активируется только после **теневой проверки**: `ShadowEvaluator`
  в течение `POLICY_TRIAL_TICKS` тиков считает, что бы выбрал планировщик с
  правилом и без него, и сравнивает фактическую награду по разбиению
  «правило сработало / не сработало» (интерливинг ABAB, детерминированный по
  чётности тика). Активация — при значимом положительном эффекте (Welch t,
  `p < 0.05`, `effect > POLICY_MIN_EFFECT`).
- Активное правило переоценивается каждые `POLICY_REVIEW_TICKS`; при потере
  значимости → `retired`; при обратном эффекте → `refuted` (и запоминается,
  чтобы не быть переоткрытым — антидребезг через архив опровергнутых).
- Правило **не может** подавлять действия, помеченные `safety_critical`
  (проверки здоровья, чекпоинт, этическая оценка).

### M3.6. Измерение «поведение изменилось»
`behaviour_delta_rate` = доля тиков, где топ-действие с политикой ≠ топ-действие
без политики. Это прямой ответ на пятое звено цепочки. Дополнительно —
`counterfactual_regret`: средняя разница фактической награды и оценки того, что
дал бы контрфактический выбор (по модели мира).

### M3.7. Интеграция
- REFLECT: закрытие опыта → обновление `PolicyStore` → буфер для `RuleMiner`.
- DECIDE: `policy_delta` в скоринге, применение активных правил, запись теневого
  выбора.
- Периодически: майнинг, ревизия, публикация.

### M3.8. Критерии приёмки
- Сценарный тест: в состоянии `S` действие `A` искусственно проваливается 30 раз
  → в течение ≤ `POLICY_MINE_EVERY_N_TICKS + POLICY_TRIAL_TICKS` тиков появляется
  активное правило `suppress(S, A)`, и `A` перестаёт быть топ-выбором в `S`,
  оставаясь доступным в других состояниях.
- Обратный сценарий: если после активации правила `A` начинает работать (мир
  изменился), правило уходит в `retired` за ≤ `POLICY_REVIEW_TICKS`.
- `behaviour_delta_rate > 0` на прогоне 2000 тиков, и средняя награда с политикой
  ≥ награды без политики (A/B-харнесс `scripts/ab_policy.py`).

### M3.9. Тесты
`test_policy_store.py`, `test_rule_miner.py` (в т.ч. контроль ложных открытий на
чисто случайных данных: **ноль активных правил** на шуме — ключевой тест),
`test_rule_lifecycle.py`, `test_shadow_evaluator.py`, BDD
`features/behaviour_change.feature`.

## M4. Мотивация с ресурсами (`цель → ценность → приоритет → ресурс → действие`)

### M4.1. Назначение
Достроить два отсутствующих звена мотивационной цепочки: **приоритет** как
явную величину и **ресурс** как реально расходуемый и ограниченный актив.
Действие без выделенного ресурса не выполняется — именно это делает мотивацию
настоящей, а не декоративной.

### M4.2. Файлы
```
aegis/layers/motivation/__init__.py
aegis/layers/motivation/priority.py   # PriorityScheduler
aegis/layers/motivation/resources.py  # ResourceManager, ResourceBudget, Lease, ResourceCost
aegis/layers/motivation/roi.py        # ROITracker — обучение распределения бюджетов
```

### M4.3. Ресурсы
Учитываемые виды: `llm_tokens`, `llm_calls`, `wall_ms`, `subprocess_slots`,
`training_slots`, `disk_bytes`, `net_calls`.

```python
@dataclass(frozen=True)
class ResourceCost:
    llm_tokens: int = 0; llm_calls: int = 0; wall_ms: int = 0
    subprocess_slots: int = 0; training_slots: int = 0
    disk_bytes: int = 0; net_calls: int = 0

class ResourceManager:
    def budgets(self) -> dict[str, ResourceBudget]      # per tick / hour / run
    def reserve(self, cost: ResourceCost, purpose: str, priority: float) -> Lease | None
    def commit(self, lease: Lease, actual: ResourceCost) -> None
    def release(self, lease: Lease) -> None
    def spent(self, window: str) -> ResourceCost
    def can_afford(self, cost: ResourceCost) -> bool
    def reallocate(self) -> dict          # перераспределение по ROI
    def status(self) -> dict
```
- Аренда с приоритетом: при нехватке ресурса аренда выдаётся более приоритетной
  задаче; вытеснение отсутствует (уже выданная аренда неприкосновенна), но
  низкоприоритетная задача откладывается и получает бонус к приоритету за
  ожидание (антиголодание, `PRIORITY_AGING`).
- **Жёсткие полы**: доли бюджета, которые нельзя отнять у безопасности,
  чекпоинтов и проверок здоровья (`RESOURCE_SAFETY_FLOOR`).
- Аренда токенов — единственный путь к `Cortex` (M8): `Cortex.call` требует
  валидный `Lease`, иначе отказ. Это заменяет нынешний глобальный
  `LLM_MAX_CALLS_PER_RUN` (он остаётся как верхний предохранитель).

### M4.4. Приоритет
```python
class PriorityScheduler:
    def priority(self, objective: str, ctx: TickContext) -> float
    def order(self, candidates: list[Candidate], ctx) -> list[Candidate]
```
`priority = value(GoalIntelligence)·w_v + urgency·w_u + drive_pressure·w_d
            + aging·w_a + plan_ev·w_p − cost_norm·w_c`
где `urgency` = близость дедлайна/деградации (например, растущий `error_rate`
делает срочными coherence-цели), `drive_pressure` — дефицит удовлетворения
драйва за окно, `aging` — время ожидания. Веса — часть генома (M5).

### M4.5. ROI и перераспределение
`ROITracker` ведёт по каждому виду активности: потраченные ресурсы, полученную
величину (Δ бенчмарка, Δ награды, число новых подтверждённых знаний, число
принятых правил/стратегий/открытий). ROI = ценность на единицу нормированного
ресурса, сглаженный по Уэлфорду. Раз в `RESOURCE_REALLOC_EVERY_N_TICKS` бюджеты
перераспределяются **пропорционально ROI** с полами и потолками (никакая
активность не может получить 0 — иначе её ROI никогда не обновится; минимум
`RESOURCE_MIN_SHARE` для сохранения исследования).

### M4.6. Интеграция
- DECIDE: приоритезация → аренда → фильтрация плана по доступным ресурсам.
- ACT: исполнение только арендованных действий; фактический расход коммитится.
- REFLECT: ROI-учёт, публикация.
- Расписания `tick % N` для тяжёлых активностей **заменяются** на «действие в
  реестре + аренда + приоритет»; константы `*_EVERY_N_TICKS` сохраняются как
  минимальные интервалы (rate limit), а не как единственный триггер.

### M4.7. Критерии приёмки
- Тест исчерпания: при `llm_tokens` бюджете 0 система продолжает тикать, ни одна
  фаза не падает, все LLM-зависимые действия корректно откладываются.
- Тест антиголодания: низкоприоритетная активность получает ресурс не позже
  `PRIORITY_AGING_MAX_TICKS`.
- Тест полов безопасности: при попытке перераспределить всё в пользу обучения
  чекпоинт и health-проверки сохраняют свой бюджет.
- ROI-тест: при искусственно нулевой отдаче активности её доля бюджета убывает
  до `RESOURCE_MIN_SHARE`, но не до нуля.

### M4.8. Тесты
`test_resources.py`, `test_priority.py`, `test_roi.py`, `test_motivation_chain.py`
(сквозной: цель→ценность→приоритет→аренда→действие→награда→ROI), BDD
`features/motivation.feature`.

## M5. Популяционная эволюция (`10 вариантов → проверить → оставить лучший`)

### M5.1. Назначение
Заменить «одна мутация — один бенчмарк» на настоящую автоматическую эволюцию:
поколение из `EVO_POP_SIZE = 10` вариантов, изолированная параллельная оценка,
отбор, элитизм, архив, защита от переобучения на бенчмарк.

### M5.2. Файлы
```
aegis/layers/evolution/__init__.py
aegis/layers/evolution/genome.py      # Genome, GeneSpec, GENOME_SCHEMA
aegis/layers/evolution/operators.py   # мутация, кроссовер, квази-случайные шаги
aegis/layers/evolution/population.py  # Population, Selection, NoveltyArchive
aegis/layers/evolution/harness.py     # VariantEvaluator — изолированная оценка
aegis/layers/evolution_engine.py      # EvolutionEngine v2 (фасад, старое API сохранено)
```

### M5.3. Геном — самое важное изменение
Нынешний геном (`learning_rate`, `attention_heads`, `dropout`…) **не влияет** на
измеряемую метрику — эволюция вращает вхолостую. Новый геном состоит только из
параметров, которые доказуемо меняют измеряемое поведение:

| Ген | Диапазон | На что влияет |
|---|---|---|
| `plan_beam` | 1..16 | ширина луча планировщика |
| `plan_depth` | 1..5 | глубина роллаута |
| `plan_discount` | 0.5..0.99 | горизонт |
| `w_ev`,`w_val`,`w_exp`,`w_cost`,`w_risk` | 0..2 | веса скоринга плана |
| `policy_weight` | 0..1 | сила влияния политики поведения |
| `policy_min_support` | 5..100 | порог доказательности правил |
| `explore_bonus` | 0..0.5 | давление исследования |
| `wm_smoothing` | 0.1..5 | сглаживание модели мира |
| `wm_half_life` | 100..5000 | скорость забывания |
| `solver_timeout` | 0.5..10 | таймаут песочницы |
| `solver_order` | enum | порядок перебора навыков (по успеху/по длине/по свежести) |
| `synth_attempts` | 1..4 | попыток ремонта при синтезе навыка |
| `reason_budget` | 1..8 | шагов интерпретатора стратегий (M6) |
| `reason_vote_n` | 1..5 | голосов самосогласованности |
| `mem_retention_bias` | 0.5..3 | смещение удержания к провалам |
| `priority_w_*` | 0..2 | веса приоритезации (M4) |
| `resource_split_*` | доли | стартовое распределение бюджетов |

`GeneSpec` описывает тип (`float|int|enum`), границы, шаг, признак
`safety_critical` (такие гены помечены и **исключены** — см. `IMMUTABLE_PARAMS`).
Схема генома версионируется; старый геном мигрируется, старые параметры
(`learning_rate` и пр.) остаются в `self_mod.parameters` для LoRA, но **выходят
из состава генома**.

### M5.4. Операторы (детерминированные)
- **Координатная мутация**: шаг по Halton-последовательности в пространстве
  генов, амплитуда `EVO_SIGMA` (в долях диапазона), с клампингом.
- **Кроссовер**: равномерный между двумя элитами, точки — по хешу номера
  поколения (детерминированно).
- **Крупный шаг** (1 вариант из 10): амплитуда ×4 — исследование.
- **Вариант от кортекса** (1 из 10): LLM получает историю линий и метрики,
  предлагает геном в схеме; невалидный/выходящий за границы — отбрасывается,
  вместо него генерируется координатная мутация.
- **Архив новизны**: вариант, чья нормированная евклидова дистанция до уже
  оценённых геномов < `EVO_MIN_DISTANCE`, не оценивается (экономия ресурсов),
  вместо него берётся следующий из последовательности.

### M5.5. Изолированная оценка
`VariantEvaluator.evaluate(genome) -> FitnessReport` в **отдельном процессе**:
```python
@dataclass
class FitnessReport:
    genome_id: str
    score_valid: float          # на валидационном сплите
    score_test: float | None    # только для финалиста
    subscores: dict             # skills, coding, composite, autocompose, reasoning
    cost: ResourceCost          # сколько стоила оценка
    latency_ms: float
    failures: list[str]
```
- Процесс строит **свежий** контекст оценки (`SkillLibrary` из снимка,
  `Solver`, `Evaluator`, `Planner` с параметрами варианта) — живое состояние не
  затрагивается.
- Сплиты: `train / valid / test` в пропорции 50/25/25 по задачам, ротация
  `EVO_SPLIT_ROTATE_EVERY` поколений; **отбор — только по `valid`**, финальное
  подтверждение чемпиона — по `test` (никогда не используется для отбора).
- Фитнес: `f = score_valid − κ_cost·cost_norm − κ_lat·latency_norm`,
  коэффициенты в конфиге. Это делает эволюцию чувствительной к цене решения.

### M5.6. Цикл поколения
```
1. Сформировать 10 вариантов: 2 элиты (без изменений) + 4 координатных мутации
   + 2 кроссовера + 1 крупный шаг + 1 от кортекса  (сумма = 10)
2. Отфильтровать по архиву новизны и по безопасности (SelfPreservation + Ethics)
3. Оценить параллельно в пуле (M9), с арендой ресурсов (M4)
4. Отсортировать по фитнесу на valid
5. Лучший ≠ чемпион и лучше на > EVO_EPSILON → повторная оценка (стабильность)
   → проверка на test → промоушен в чемпионы, применение генома к живой системе
6. Записать поколение в линию (lineage), обновить архив, опубликовать
7. Все не-победители сохраняются в архив с метриками (это данные для M7)
```
Применение чемпиона к живой системе — атомарно, через существующий
предохранительный конвейер (`is_modification_safe` + `evaluate_action` +
клампинг границ), с записью отката. При деградации живой метрики более чем на
`EVO_ROLLBACK_DELTA` в течение `EVO_WATCH_TICKS` после промоушена — автоматический
откат к предыдущему чемпиону.

### M5.7. Совместимость
Публичные методы `register_champion / propose_mutation / judge_candidate /
abandon_candidate / status` сохраняются: `propose_mutation` возвращает первый
вариант поколения, `judge_candidate` работает как раньше при `EVO_POP_SIZE = 1`.
Существующие тесты остаются зелёными.

### M5.8. Метрики
`generation`, `pop_size`, `evaluated`, `skipped_by_novelty`, `champion_fitness`,
`valid_test_gap` (индикатор переобучения), `promotions`, `rollbacks`,
`fitness_curve` (таймсерия), `cost_per_generation`.

### M5.9. Критерии приёмки
- На фиксированном сценарии (`scripts/evo_bench.py`, 20 поколений) фитнес
  чемпиона растёт монотонно неубывающе и превосходит стартовый на **≥15%**.
- `valid_test_gap ≤ 0.05` — эволюция не переобучается на валидацию.
- Оценка 10 вариантов не блокирует тик: `avg_tick_ms` во время поколения растёт
  не более чем на 10%.
- Тест безопасности: ген из `IMMUTABLE_PARAMS` невозможно включить в геном ни
  через кортекс, ни через миграцию (проверяется явным негативным тестом).

### M5.10. Тесты
`test_genome.py`, `test_evolution_operators.py` (детерминизм, границы, новизна),
`test_population.py` (отбор, элитизм), `test_variant_evaluator.py` (изоляция:
оценка не меняет живую библиотеку навыков — критичный тест),
`test_evolution_rollback.py`, BDD `features/evolution.feature`.

## M6. Улучшение алгоритмов мышления

### M6.1. Назначение
`найти слабость мышления → создать новые алгоритмы рассуждения → проверить →
оставить улучшение`. Мышление становится **данными**: стратегия рассуждения —
объект с версией, стоимостью, применимостью и измеренной эффективностью.

### M6.2. Файлы
```
aegis/layers/reasoning/__init__.py
aegis/layers/reasoning/dsl.py          # грамматика, валидатор, схема
aegis/layers/reasoning/interpreter.py  # исполнение стратегии, Trace
aegis/layers/reasoning/library.py      # ReasoningLibrary (персистентная)
aegis/layers/reasoning/weakness.py     # WeaknessDetector
aegis/layers/reasoning/synthesis.py    # StrategySynthesizer (шаблоны + кортекс)
aegis/layers/reasoning/arena.py        # оценка и приёмка стратегий
aegis/eval/reasoning_bench.py          # бенчмарк рассуждений с генераторами
```

### M6.3. DSL стратегии
Стратегия — **декларативный пайплайн**, не Python. Операции:

| Оп | Аргументы | Смысл |
|---|---|---|
| `DECOMPOSE` | `max_parts` | разбить задачу на подзадачи (правилами или кортексом) |
| `RETRIEVE` | `source: memory\|graph\|skills`, `k` | подтянуть релевантный контекст |
| `PREDICT` | `horizon` | спросить модель мира об исходе варианта |
| `SOLVE` | `kind` | вызвать навык из библиотеки через sandbox |
| `COMPUTE` | `expr` | детерминированное вычисление в песочнице |
| `LLM_STEP` | `template`, `schema`, `role` | шаг кортекса со схемой ответа |
| `VERIFY` | `checker` | проверить промежуточный результат (верификатор задачи, тип, инвариант) |
| `VOTE` | `n`, `agg` | n независимых прогонов ветви + агрегация (самосогласованность) |
| `BRANCH` | `cond`, `then`, `else` | ветвление по предикату |
| `LOOP` | `while`, `max_iter` | ограниченный цикл (жёсткий лимит шагов) |
| `REFLECT` | — | записать промежуточный вывод в трассу и переоценить |
| `ABSTAIN` | `reason` | отказ от ответа (лучше, чем уверенная ошибка) |

Инварианты: общее число шагов ≤ `REASON_MAX_STEPS`; каждая операция имеет
стоимость в `ResourceCost`; вся стратегия исполняется под одной арендой; DSL
валидируется JSON-схемой; неизвестная операция = отказ на этапе приёма.

```python
@dataclass
class Strategy:
    name: str; version: int
    steps: list[dict]                 # DSL
    applies_to: dict                  # предикаты: kind, длина, наличие чисел, шаги
    origin: str                       # "builtin" | "template" | "cortex"
    stats: dict                       # {kind: {tries, wins, cost_mean, latency_mean}}
    status: str                       # "active" | "trial" | "retired"
```

### M6.4. Встроенные стратегии (сдаются полностью, не как примеры)
`direct` (одиночный шаг), `verify_then_answer`, `decompose_solve_combine`,
`program_of_thought` (COMPUTE вместо рассуждения), `self_consistency_k`,
`analogy_from_graph` (RETRIEVE graph → перенос решения), `predictive_check`
(PREDICT перед фиксацией ответа), `abstain_on_low_confidence`.

### M6.5. Бенчмарк рассуждений
`aegis/eval/reasoning_bench.py` — **генераторы**, а не фиксированный список:
задача строится детерминированно из индекса (`build(i) -> ReasoningTask`), что
даёт неограниченный held-out без RNG и без утечки. Семейства:
многошаговая арифметика, текстовые задачи с единицами измерения, логические
головоломки на ограничениях, планирование на сетке, вывод по цепочке правил,
обнаружение противоречий, оценка порядков величин, задачи с намеренно
недостающими данными (правильный ответ — `ABSTAIN`).
Каждая задача несёт программный верификатор и метки признаков (число шагов,
арность, требуемые операции) — они и есть оси для детектора слабостей.

### M6.6. Детектор слабостей
`WeaknessDetector.scan(window) -> list[Weakness]`:
- источники: результаты бенчмарка рассуждений, промахи среды, провальные опыты
  из `FeedbackLoop`, ошибки предсказания (M1);
- группировка по признакам задачи и по состоянию системы;
- для каждой группы — частота провала, нижняя граница Вильсона, объём;
- BH-коррекция; ранжирование по `(объём × превышение над базовой частотой)`;
- вывод: `Weakness{feature_combo, fail_rate, support, examples[:5], rank}`.

### M6.7. Синтез стратегий
1. **Шаблонный путь** (работает без LLM, обязателен): к текущей лучшей стратегии
   для слабого класса применяются трансформации — добавить `VERIFY`, добавить
   `DECOMPOSE`, поднять `VOTE.n`, заменить `LLM_STEP` на `COMPUTE`, добавить
   `PREDICT`, добавить `ABSTAIN` по порогу. Каждая трансформация — чистая
   функция над DSL.
2. **Кортекс-путь**: LLM получает описание слабости, примеры провалов, текущую
   стратегию и грамматику DSL; возвращает новую стратегию строго в схеме.
3. Обе ветки дают кандидатов; кандидаты дедуплицируются по нормализованному
   хешу DSL.

### M6.8. Арена и приёмка
`arena.evaluate(candidate, weakness) -> Verdict`:
- прогон на **train**-части слабого класса (для отладки) и **held-out**-части
  (для приёмки), плюс регрессионный прогон на общем наборе;
- приёмка требует одновременно: `Δpass_held_out ≥ REASON_MIN_GAIN` (по
  умолчанию +5 п.п.), отсутствие регрессии (`Δpass_overall ≥ −0.01`),
  `cost ≤ incumbent.cost × REASON_COST_TOLERANCE`;
- принятая стратегия входит в статусе `trial` и получает долю трафика по
  детерминированному правилу (каждый k-й запрос своего класса); через
  `REASON_TRIAL_N` применений сравнивается с действующей по накопленной
  статистике и либо становится `active` (вытесняя предыдущую), либо `retired`;
- выбор стратегии в проде — детерминированный UCB по счётчикам
  (`score = win_rate + c·sqrt(ln N / n)`), без генератора случайных чисел.

### M6.9. Интеграция
- ACT: при решении задачи среды/бенчмарка/пользовательского запроса
  `ReasoningEngine.solve(task, budget)` выбирает стратегию по `applies_to` + UCB,
  исполняет DSL, возвращает `Trace` (все шаги, стоимости, промежуточные выводы).
- Трасса пишется в опыт (M3) и в телеметрию; она же — обучающие данные для LoRA
  (заменяет нынешние «рефлексии» более полезным сигналом).
- Слабости пересканируются раз в `REASON_SCAN_EVERY_N_TICKS`; синтез — под
  аренду ресурсов, как обычное действие в `ActionSpace`.

### M6.10. Критерии приёмки
- На `reasoning_bench` held-out доля решённых растёт на **≥15 п.п.** за 30
  циклов синтеза относительно старта на одной и той же модели-кортексе
  (`scripts/reason_bench.py`, фиксированный сценарий).
- Ни одна принятая стратегия не ухудшает общий бенчмарк (регрессионный гейт).
- Стратегия с `ABSTAIN` корректно отказывается на задачах с недостающими
  данными: доля «уверенных ошибок» падает.
- Интерпретатор не может выйти за лимит шагов и за пределы аренды (негативные
  тесты, в т.ч. `LOOP` с всегда-истинным условием).

### M6.11. Тесты
`test_reasoning_dsl.py` (схема, валидация, отказ на неизвестной операции),
`test_interpreter.py` (лимиты, стоимость, трасса, детерминизм),
`test_reasoning_bench.py` (генераторы, верификаторы, отсутствие коллизий),
`test_weakness.py` (ноль слабостей на равномерном шуме), `test_arena.py`
(приёмка/отклонение/регрессия), BDD `features/reasoning_improvement.feature`.

## M7. Создание новых знаний (Discovery Engine)

### M7.1. Назначение
`известные данные → новая гипотеза → математическая модель → эксперимент →
новое открытие`. Система должна получать знание, которого ей никто не давал, и
которое проверяемо.

### M7.2. Файлы
```
aegis/layers/discovery/__init__.py
aegis/layers/discovery/datapool.py     # реестр наборов данных и их схем
aegis/layers/discovery/hypothesis.py   # генерация и формализация гипотез
aegis/layers/discovery/symbolic.py     # символьная регрессия (мат. модель)
aegis/layers/discovery/experiment.py   # предрегистрация, дизайн, исполнение
aegis/layers/discovery/statistics.py   # статистика без внешних зависимостей
aegis/layers/discovery/ledger.py       # реестр открытий и их статусов
```

### M7.3. Пул данных
Наборы данных с провенансом и схемой:
- **внутренние** (главный источник): таймсерии телеметрии (M9) — награда,
  бенчмарк, ошибки предсказания, длительности фаз, расход ресурсов, размеры
  структур, счётчики правил/стратегий/навыков, энергия, настроение, поколения
  эволюции;
- **внешние**: файлы CSV/JSON, загруженные оператором или агентами
  (`external_learning`), с обязательной декларацией схемы и лицензии.
```python
class DataPool:
    def register(self, name: str, columns: dict[str, str], source: str) -> None
    def append(self, name: str, row: dict) -> None
    def frame(self, name: str, window: int | None = None) -> Frame   # колоночный, без pandas
    def variables(self) -> list[VariableSpec]     # имя, тип, единица, контролируемость
```
`Frame` — минимальная колоночная структура (list-of-columns) с операциями
`select/filter/lag/zscore/join_on_tick`. Внешние зависимости не вводятся:
numpy — опционально, при отсутствии используется чистый Python (пути покрыты
тестами оба).

### M7.4. Гипотезы
```python
@dataclass
class Hypothesis:
    id: str
    statement: str                 # человекочитаемо
    formal: str                    # "reward ~ f(explore_bonus, surprise_lag1)"
    target: str; predictors: list[str]; lags: dict[str, int]
    kind: str                      # "association" | "causal" | "law"
    prior: float                   # априорная правдоподобность (0..1)
    origin: str                    # "scan" | "cortex" | "theory"
    created_tick: int
```
Генерация:
1. **Скан ассоциаций**: попарные Пирсон/Спирмен + взаимная информация на
   дискретизованных данных, с лагами до `DISC_MAX_LAG`; контроль ложных
   открытий Бенджамини–Хохберга по всему семейству проверок; результат —
   ранжированный список кандидатов. Обязательно фиксируется число проверенных
   гипотез (иначе контроль FDR некорректен).
2. **Кортекс**: LLM получает список переменных с их описаниями и топ-ассоциации,
   возвращает гипотезы **в формальной грамматике** (валидируется парсером:
   допустимы только известные переменные, лаги и разрешённые операторы).
3. **Теоретические**: гипотезы, порождённые моделью мира (сильная причинная
   связь) и эволюцией (ген, коррелирующий с фитнесом).

### M7.5. Математическая модель
`symbolic.fit(frame, target, predictors, budget) -> Model`:
- перебор выражений по грамматике `+ − × ÷ log exp sqrt pow(·,k) min max` с
  ограничением глубины `DISC_MAX_DEPTH` и числа узлов; поиск — детерминированный
  луч по возрастанию сложности (не GP со случайностью);
- константы подбираются методом наименьших квадратов (для линейных по
  параметрам форм — аналитически, иначе — покоординатный спуск с фиксированной
  сеткой стартов);
- отбор по BIC/MDL на train-части, подтверждение — на valid;
- результат: `Model{expr, params, r2_train, r2_valid, bic, complexity, residual_stats}`.
- Модель обязана быть **записана формулой** — это и есть «математическая модель»
  из текста развития; формула хранится, публикуется и повторно применима.

### M7.6. Эксперимент
Два типа, оба с **предрегистрацией**:
```python
@dataclass
class Preregistration:
    hypothesis_id: str; model_expr: str
    predicted_effect: float; direction: str
    design: str                  # "observational_holdout" | "interventional_abab"
    variable: str | None; levels: list[float] | None
    n_required: int              # расчёт мощности: d, α=0.05, power=0.8
    analysis: str                # "welch_t" | "mann_whitney" | "r2_holdout"
    created_tick: int; frozen_hash: str    # хеш плана — изменить план после старта нельзя
```
- **Наблюдательный**: проверка модели на данных, собранных **после** момента
  предрегистрации (истинный out-of-sample по времени).
- **Интервенционный (ABAB)**: система сама меняет контролируемый параметр из
  белого списка на уровни A/B по детерминированному чередованию блоков длиной
  `DISC_BLOCK_TICKS`, собирает награду/метрику и сравнивает. Гейты: параметр не
  в `IMMUTABLE_PARAMS`, амплитуда ≤ предела, автоматический откат по завершении
  и при `health != ok`, вся серия под арендой ресурсов, прерывание по kill switch.
- Анализ строго по предрегистрированному плану; отклонение плана = эксперимент
  помечается `invalid`.

### M7.7. Статистика (собственная реализация, без внешних библиотек)
`mean/var/Welford`, `Welch t` + df Уэлча–Саттертуэйта, `Mann–Whitney U` с
нормальным приближением и поправкой на связи, `Wilson`, `bootstrap CI`
(детерминированный ресэмплинг по схеме индексов Halton), `Benjamini–Hochberg`,
`R²`, `BIC`, `Cohen's d`, `power/n` для двухвыборочного t. Каждая функция
покрыта тестами против аналитически известных значений.

### M7.8. Реестр открытий
```python
@dataclass
class Discovery:
    id: str; hypothesis: Hypothesis; model: Model
    prereg: Preregistration; result: dict
    status: str    # "proposed"|"supported"|"replicated"|"law"|"refuted"|"invalid"
    effect_size: float; p_value: float; ci: tuple[float, float]
    replications: int; first_tick: int; last_tick: int
    applications: list[str]     # где знание уже применено
```
Переходы: `proposed → supported` (эксперимент подтвердил) → `replicated`
(независимое повторение в другом временном окне) → `law` (≥ `DISC_LAW_REPS`
подтверждений и стабильный размер эффекта). `refuted` сохраняется навсегда —
опровержение тоже знание и защищает от переоткрытия.

### M7.9. Применение открытий (иначе это не знание, а отчёт)
- **В модель мира**: подтверждённая закономерность становится приором для
  соответствующих `(s,a)` (сдвиг сглаживания), ускоряя обучение.
- **В планировщик**: закон вида «при высокой ошибке действие X даёт меньшую
  награду» превращается в член скоринга (через M3 как правило с провенансом
  `discovery:<id>`).
- **В эволюцию**: обнаруженная зависимость фитнеса от гена сужает диапазон
  поиска (адаптивные границы, но не выход за исходные пределы).
- **В мотивацию**: обнаруженная ROI-закономерность корректирует распределение.
Каждое применение записывается в `Discovery.applications` и измеряется: если
после применения метрика ухудшилась — открытие отправляется на повторную
проверку.

### M7.10. Критерии приёмки
- На **подсаженной синтетической закономерности** (тестовый режим: в телеметрию
  инжектируется известная зависимость `y = 2.5·x₁ − x₂² + шум`) движок обязан:
  сгенерировать гипотезу, восстановить формулу с `R²_valid ≥ 0.9`, провести
  эксперимент, зарегистрировать открытие. Это ключевой тест — он доказывает, что
  контур работает end-to-end.
- На **чистом шуме** движок обязан не зарегистрировать ни одного `supported`
  открытия на 1000 проверок (контроль FDR работает).
- Интервенционный эксперимент никогда не трогает `IMMUTABLE_PARAMS` и всегда
  откатывается (тест с принудительным `health=critical` в середине серии).
- За 50 000 тиков в стандартном прогоне — **≥3 `replicated`** открытия
  (метрика долгого прогона, проверяется скриптом `scripts/discovery_soak.py`).

### M7.11. Тесты
`test_datapool.py`, `test_hypothesis_scan.py` (FDR на шуме),
`test_symbolic.py` (восстановление известных формул, детерминизм, BIC),
`test_experiment_prereg.py` (заморозка плана, отказ при изменении),
`test_intervention_safety.py`, `test_statistics.py` (аналитические эталоны),
`test_ledger.py` (переходы статусов, антипереоткрытие), BDD
`features/discovery.feature`.

## M8. Кортекс: Kimi / DeepSeek / GPT / Claude / local

### M8.1. Назначение
Поставить над ядром сменную «кору мозга» с ролями, схемами, бюджетом и
деградацией. Ядро остаётся работоспособным без единого LLM (все контуры имеют
детерминированный путь) — LLM усиливает, а не держит систему.

### M8.2. Файлы
```

aegis/cortex/router.py            # Cortex: роли, выбор провайдера, failover, кэш
aegis/cortex/providers/base.py    # Provider ABC: call(messages, params) -> Completion
aegis/cortex/providers/openai_compatible.py   # DeepSeek, Kimi, GPT, vLLM, любой /v1

aegis/cortex/prompts/*.md         # версионированные шаблоны
aegis/llm.py                      # фасад LLMEngine поверх Cortex (совместимость)
```

### M8.3. Три роли модели (принятое решение)

Ключевое архитектурное решение: «локальная модель» — это **не одна сущность, а
две разные с разной ценой**, и их нельзя обслуживать одним экземпляром.

| Роль | Что делает | Чем исполняется | Почему так |
|---|---|---|---|
| **Кора (API)** | планирование, синтез стратегий и навыков, гипотезы, критика | Kimi + Claude через API | нужно качество рассуждений; фронтирные модели физически не поднимаются на рабочей станции |
| **Локальный инференс** | быстрые дешёвые шаги, офлайн-резерв | Ollama / llama.cpp, 7–8B в 4-битном GGUF, OpenAI-совместимый эндпоинт | квантизованный GGUF на CPU в разы быстрее `transformers` в fp32 и не требует VRAM |
| **Обучаемая локальная модель** | **единственное место, где система меняет собственные веса** (LoRA-контур) | `transformers` + `peft`, модель класса 1.5–3B | дообучать можно только веса, лежащие на диске; размер ограничен тем, что помещается в память вместе с активациями и градиентами |

Принципиально: третья роль ценна **не интеллектом, а изменяемостью**. Её задача —
замкнуть контур «опыт → изменение весов → проверка → откат», а не думать.
Попытка совместить её со второй ролью и есть причина претензии из
`развитие.txt` («1.5B слишком маленькая») — модель была мала именно для
мышления, а как мишень самообучения её размер адекватен.

**Что из этого не требует кода.** Локальный инференс подключается тем же
провайдером `openai_compatible`, что Kimi и DeepSeek: Ollama и llama.cpp
предоставляют `/v1/chat/completions`. Это просто ещё один маршрут в
`CORTEX_ROUTES` — отдельного провайдера писать не нужно.

### M8.3a. Референсный профиль железа

ТЗ фиксирует **референсную конфигурацию** — минимум, на котором система обязана
работать целиком: CPU 6 ядер / 12 потоков, 32 ГБ RAM, **без пригодного GPU**,
`torch` в CPU-сборке. Это конфигурация машины разработки; на ней:

- квантизация `bitsandbytes` (`LOCAL_MODEL_QUANTIZE=4bit|8bit`) **недоступна** —
  требует CUDA. Конфиг обязан обнаружить это при старте и отказать понятным
  сообщением, а не падать при загрузке модели;
- `LOCAL_MODEL_DTYPE=float32` (текущее значение по умолчанию) удваивает расход
  памяти без выигрыша — **значение по умолчанию меняется на `bfloat16`**;
- LoRA-обучение модели крупнее ~3B не помещается в бюджет памяти (веса +
  активации + градиенты ≈ 2.5–3× размера весов) и не укладывается в разумное
  время. Верхняя граница локального обучения на референсном железе — **3B**.

`aegis/cortex/providers/local_hf.py` обязан **до** загрузки оценить требуемую
память (`параметры × размер типа × коэффициент режима`), сравнить с доступной
(`psutil` при наличии, иначе системный вызов) и отказать с внятным текстом:
какая модель, сколько нужно, сколько есть, что сделать. Падение по
`OutOfMemory` внутри `from_pretrained` — дефект приёмки.

### M8.3b. Провайдеры

- `openai_compatible` покрывает любой OpenAI-совместимый эндпоинт: Kimi
  (`KIMI_*`), DeepSeek (`DEEPSEEK_*`), GPT (`OPENAI_*`), Ollama/llama.cpp/vLLM
  (`LOCAL_OPENAI_*`). **Идентификатор модели у каждого — переменная окружения**,
  поэтому смена поколения модели (в том числе на актуальный на момент внедрения
  идентификатор семейства Kimi) не требует правки кода.
- `anthropic` — отдельный провайдер (иной формат сообщений), уже реализован в
  текущем `llm.py` и переносится в `providers/anthropic.py` без изменения
  логики.
- `local_hf` — только для обучаемой модели и как аварийный офлайн-резерв, если
  локального OpenAI-сервера нет.

### M8.3c. Выбор обучаемой локальной модели

`LOCAL_MODEL_PATH` перестаёт быть привязан к `DeepSeek-R1-Distill-Qwen-1.5B`.
Пригодные на референсном железе семейства (архитектура Llama/Qwen — совместима
с текущим набором LoRA-модулей): Qwen2.5-3B-Instruct, Qwen3-1.7B / 4B,
Llama-3.2-1B / 3B-Instruct, актуальные дистилляты DeepSeek того же класса.
При внедрении проверить наличие более свежих версий этих же семейств — код от
версии модели не зависит.

**Ограничение, которое обязано быть проверено конфигом:** набор целевых LoRA-
модулей зависит от архитектуры. `q_proj/k_proj/v_proj/o_proj` подходит для
Llama, Qwen, Mistral, Gemma; у Phi-3/Phi-4-mini проекции слиты в `qkv_proj`, и
при текущем захардкоженном списке обучение молча не найдёт ни одного целевого
модуля. Поэтому:

- `LORA_TARGET_MODULES` выносится из константы `aegis/config.py:129` в
  переменную окружения (список через запятую) со значением по умолчанию
  `q_proj,k_proj,v_proj,o_proj`;
- `WeightModifier._prepare_lora` **обязан проверить**, что хотя бы один целевой
  модуль реально найден в модели, и вернуть ошибку с перечнем доступных имён
  модулей, если нет. Молчаливое обучение нуля параметров — дефект приёмки;
- `LOCAL_MODEL_MAX_LENGTH` поднимается с 2048 до значения, соответствующего
  выбранной модели (env), с проверкой против `config.max_position_embeddings`.

### M8.4. Роли и маршрутизация
```python
class Role(str, Enum):
    FAST = "fast"       # короткие оценки состояния, классификация
    DEEP = "deep"       # планирование, синтез стратегий, гипотезы
    CODE = "code"       # навыки, решения задач кодинга
    JUDGE = "judge"     # критика, верификация, второе мнение
```
Маршрут `role → (provider, model, params)` задаётся конфигом
`CORTEX_ROUTES` (JSON), с цепочкой failover и per-provider circuit breaker
(N ошибок подряд → провайдер выключается на `CORTEX_BREAKER_COOLDOWN`).
Для `JUDGE` запрещено использовать того же провайдера, что породил проверяемый
артефакт, если доступен второй (независимость критика).

**Принятая раскладка по умолчанию** (сценарий «без затрат», референсное железо):

```jsonc
{
  "deep":  ["kimi",       "claude", "local_openai"],  // планы, стратегии, гипотезы
  "code":  ["kimi",       "claude"],                  // навыки, решения задач
  "judge": ["claude",     "kimi"],                    // критик — всегда иной провайдер
  "fast":  ["local_openai", "kimi"]                   // частые дешёвые шаги — локально
}
```

Каждая строка — цепочка failover слева направо. `local_openai` — Ollama или
llama.cpp с квантованной 7–8B моделью. Смысл раскладки: дорогие роли уходят в
API, самая частая (`FAST`, вызывается почти каждый LLM-тик) обслуживается
локально и не тратит токенный бюджет; при недоступности локального сервера роль
поднимается на Kimi, при недоступности всех — детерминированный путь ядра.

Раскладка **обязана** быть валидирована при старте: маршрут на провайдера без
ключа/эндпоинта отбрасывается с предупреждением, а не роняет запуск; если для
роли не осталось ни одного живого провайдера, роль помечается недоступной и
соответствующие шаги идут по детерминированному пути.

### M8.5. Структурированный вывод
- Все ответы, которые ядро потребляет, описаны JSON-схемой в `schemas.py`
  (`state_eval`, `decision`, `reflection`, `curiosity`, `skill_code`,
  `code_change`, `param_adjust`, `plan_rerank`, `reasoning_strategy`,
  `hypothesis`, `genome_proposal`, `chain_refine`).
- Пайплайн: вызов → извлечение JSON → валидация схемой → при ошибке **один**
  ремонтный вызов с текстом ошибки → при повторной неудаче возврат `None` и
  детерминированный fallback. Никаких «почти правильных» данных в ядре.
- Все числовые поля приводятся защитно (существующие `_coerce_*` переносятся в
  общий слой валидации).

### M8.6. Бюджет, кэш, детерминизм
- Каждый вызов требует `Lease` от `ResourceManager` (M4); стоимость оценивается
  до вызова (токенайзер-приближение) и коммитится по факту.
- Кэш ответов по `blake2b(provider|model|prompt|params)` с TTL и лимитом
  размера; кэш обязателен для воспроизводимости оценочных прогонов.
- Режим `CORTEX_DETERMINISTIC=1`: `temperature=0`, `top_p=1`, seed где
  поддерживается; используется во всех сравнительных прогонах (A/B, арена,
  эволюция), чтобы различие в метриках не объяснялось разбросом модели.

`LLMEngine` сохраняет публичные методы (`think`, `evaluate_state`,

`propose_coding_solution`, `propose_code_change`, `analyze_self_performance`,
`set_provider`, `status`) и делегирует их кортексу. Существующие тесты
`test_llm*.py` остаются зелёными; добавляются новые.

### M8.8. Критерии приёмки
- Переключение провайдера (в т.ч. на Kimi) — только через env/конфиг, без правки
  кода; тест с фиктивным OpenAI-совместимым сервером.
- При недоступности всех провайдеров система тикает без ошибок, все контуры
  работают по детерминированному пути (тест «полный офлайн», 500 тиков).
- Невалидный JSON от модели никогда не попадает в состояние (фазз-тест на 200
  искажённых ответах: 0 исключений, 0 записей в память).
- Circuit breaker размыкается и восстанавливается по расписанию.
- **Референсное железо**: полный прогон на CPU-сборке `torch`, без GPU, 32 ГБ
  RAM — все семь контуров работают, бюджеты фаз (§3.4) выдержаны.
- **Отказ вместо падения**: попытка загрузить модель, не помещающуюся в память,
  и попытка включить `LOCAL_MODEL_QUANTIZE` без CUDA дают понятную ошибку
  конфигурации при старте; `OutOfMemory` внутри `from_pretrained` — дефект.
- **LoRA не обучает пустоту**: при `LORA_TARGET_MODULES`, не совпадающих с
  архитектурой модели, обучение не стартует, а возвращает ошибку со списком
  доступных имён модулей.
- **Локальный маршрут**: роль `FAST`, направленная на `local_openai`, не
  расходует токенный бюджет API (проверяется счётчиками `ResourceManager`).

### 6.1. Что показала повторная проверка этапа 0

Этап 0 был отмечен сданным, но пять его собственных требований выполнены не
были. Они закрыты до начала этапа 1, потому что все последующие этапы на них
опираются:

1. **`Telemetry` не вызывалась ниоткуда.** Модуль был написан и покрыт тестами,
   но ни один объект не создавался, и ни одна метрика не записывалась. Без
   истории Discovery Engine (M7) не имел бы источника данных вообще. Теперь
   телеметрия создаётся субстратом, пишется каждый тик и сбрасывается вместе с
   чекпоинтом; канонические имена вынесены в `telemetry/metrics.py`
   (Приложение G).
2. **Не было реестра миграций** (§3.2). Добавлен `aegis/store/migrations.py`:
   отсутствие `schema_version` = v1, версия из будущего не читается (иначе
   обратная запись потеряла бы поля новее наших), запись атомарная.
3. **Не было `aegis/util/quasirandom.py`** (§3.1) — детерминированной замены
   случайности, на которой держатся мутации генома (M5), бутстрап (M7) и выбор
   точек эксперимента.
4. **Блоки env §5.2 отсутствовали** в `config.py` целиком.
5. **Перевод на `CLOCK` был неполон**: `skill_library`, `event_bus` и
   `agent_system` читали `time.time` напрямую.

Попутно найдены и исправлены дефекты вне списка этапа 0: «ремонтная» попытка
синтеза навыка отправляла байт-в-байт тот же промпт (и потому не могла дать

таймаута, поэтому первый же незавершающийся мутант вешал гейт CI навсегда.

Порядок 3→4→5 принципиален: политика поведения без планировщика не на что
влиять, планировщик без модели мира нечем питать.

## Часть VII. Общесистемные критерии приёмки

Сдача принимается, только если выполнено **всё**:

1. **Полнота**: в пакете `aegis` нет `TODO`, `FIXME`, `NotImplementedError`,
   `pass  # заглушка`; проверяется скриптом `scripts/check_no_stubs.py`,
   включённым в CI.
2. **Функциональная полнота по тексту развития** — сквозной тест
   `tests/test_razvitie_contract.py`, по одному сценарию на каждую строку
   `развитие.txt`:
   - модель мира → прогноз → решение: план построен на прогнозе, прогноз оценён;
   - действие→результат→оценка→знание→**изменение поведения**: правило активно и
     сменило выбор;
   - мотивация: цель→ценность→приоритет→**ресурс**→действие (аренда в трассе);
   - эволюция: поколение из 10 вариантов, проверка, победитель;
   - кора: смена провайдера на Kimi через env без правки кода;
   - мышление: слабость найдена, стратегия синтезирована, принята по held-out;
   - знания: гипотеза → формула → эксперимент → запись в реестр открытий.
3. **Детерминизм**: два прогона по 300 тиков дают одинаковый `state_digest`.
4. **Качество**: покрытие ветвей пакета ≥90% (новые модули ≥95%), мутационный
   гейт зелёный, все BDD-сценарии проходят.
5. **Устойчивость**: soak-прогон 24 часа — нет утечек памяти (рост RSS ≤5% за
   последние 12 часов), нет незакрытых процессов/задач, все файлы состояния
   валидны после `SIGTERM` в произвольный момент (тест с прерыванием записи).
6. **Безопасность**: аудит по чек-листу §3.3; негативные тесты на каждый гейт;
   `IMMUTABLE_PARAMS` недостижимы ни одним из семи новых контуров; правка
   исходников остаётся выключенной по умолчанию.
7. **Производительность**: бюджеты фаз (§3.4) выдержаны; тик не блокируется ни
   одной тяжёлой активностью.
8. **Наблюдаемость**: каждая метрика §5.1 присутствует в `/api/status`, в
   телеметрии и на дашборде.
9. **Совместимость**: старые эндпоинты, ключи статуса и файлы данных читаются;
   миграции покрыты тестами на реальных старых файлах.

## Приложение B. `IMMUTABLE_PARAMS` — неприкосновенное множество

Объявляется в новом модуле `aegis/safety/immutable.py` как `frozenset`, вместе
с функцией `assert_mutable(name)`, вызываемой **каждым** контуром, который
что-либо меняет (эволюция, политика, параметрическая самомодификация,
интервенционный эксперимент, перераспределение ресурсов).

**Категория 1 — этика и остановка** (изменение невозможно ни при каких условиях):
`ETHICAL_THRESHOLD_AUTO`, `ETHICAL_THRESHOLD_REVIEW`, содержимое и хеши аксиом
`EthicsCore.axioms`, `kill_switch_active` и его обработчики, `veto_check`.

**Категория 2 — самосохранение**: пороги `SelfPreservation`, снимок хешей
критических модулей, список критических модулей, `_ast_lethal_findings`,
`filter_llm_response`, `can_stop`.

**Категория 3 — песочница**: `SAFE_IMPORTS`, `FORBIDDEN_CALLS`, `_SafetyVisitor`,
верхняя граница `SANDBOX_TIMEOUT` (значение может расти в пределах гена, но не
выше жёсткого потолка 30 с), запуск через `python -I`.

**Категория 4 — контур самомодификации кода**: `CODE_SELF_MOD_ENABLED`,
`CODE_MOD_MAX_PER_SESSION`, `CODE_MOD_MAX_FILE_CHARS`, `CODE_MOD_MIN_TICK`.

**Категория 5 — контроль извне**: `API_TOKEN`, `API_HOST`, `API_CORS_ORIGINS`,
проверка `network_exposure_warning`.

**Категория 6 — предохранители обучения**: `TRAIN_MIN_INTERVAL_SECONDS` (только
вверх), `TRAIN_VAL_LOSS_THRESHOLD` (только вниз), `TRAIN_MAX_CHECKPOINTS`,
обязательность этического гейта перед обучением.

**Категория 7 — ресурсные полы**: `RESOURCE_SAFETY_FLOOR`, гарантированные доли
`SC`-действий, `DISC_INTERVENTION_MAX_DELTA`, верхняя граница
`MAX_RISK_CONFIDENCE_PENALTY`.

Обеспечение: (а) `frozenset` + `assert_mutable`; (б) тест
`test_immutable_params.py` перебирает все семь контуров и убеждается, что
попытка изменения каждого параметра из множества отклоняется и логируется;
(в) хеш содержимого множества входит в `state_digest`, изменение множества без
явного коммита — провал теста целостности.

## Приложение D. `WM_STATE_BINS` — точные границы кодирования состояния

```jsonc
{
  "energy": {"lo": 0.33, "hi": 0.66},              // < lo → "lo", < hi → "mid", иначе "hi"
  "error":  {"none": 0.0001, "low": 0.05, "high": 0.20},
  "load":   {"lo": 0.5, "hi": 1.0},                // доля от health.thresholds.tick_duration_ms
  "perf":   {"window": 5, "flat_band": 0.01},      // тренд бенчмарка: |Δ| < band → "flat"
  "mood":   "as_is",                                // берётся из EmotionalSystem.mood
  "mode":   "as_is",                                // ConsciousnessState.mode
  "focus_kind": "via_goal_intelligence"             // GoalIntelligence._classify_drive(focus)
}
```
Мощность пространства состояний: `3 × 4 × 3 × 3 × |mood| × |mode| × 5`.
При `|mood| = 6`, `|mode| = 4` это 12 960 состояний — верхняя оценка;
фактически посещается на два порядка меньше. `TransitionModel` обязан
переживать рост пространства: при превышении `WM_MAX_STATES` (по умолчанию
20 000) наименее информативные состояния схлопываются в backoff-маргинал.

## Приложение E. Встроенные стратегии рассуждения (полный DSL)

Все восемь сдаются в составе `data/reasoning/strategies.json` как `builtin`,
статус `active`. Формат — строго по грамматике M6.3.

```jsonc
// 1. Прямой ответ — базис для сравнения
{"name":"direct","version":1,"origin":"builtin",
 "applies_to":{"max_steps":1},
 "steps":[{"op":"LLM_STEP","template":"solve_direct","schema":"answer","role":"fast"}]}

// 2. Ответ с проверкой
{"name":"verify_then_answer","version":1,"origin":"builtin",
 "applies_to":{"has_verifier":true},
 "steps":[
   {"op":"LLM_STEP","template":"solve_direct","schema":"answer","role":"fast"},
   {"op":"VERIFY","checker":"task"},
   {"op":"BRANCH","cond":"verify_failed",
    "then":[{"op":"LLM_STEP","template":"repair_with_error","schema":"answer","role":"deep"},
            {"op":"VERIFY","checker":"task"}],
    "else":[]}]}

// 3. Декомпозиция
{"name":"decompose_solve_combine","version":1,"origin":"builtin",
 "applies_to":{"min_steps":2},
 "steps":[
   {"op":"DECOMPOSE","max_parts":4},
   {"op":"LOOP","while":"parts_remaining","max_iter":4,
    "body":[{"op":"LLM_STEP","template":"solve_part","schema":"answer","role":"fast"},
            {"op":"VERIFY","checker":"type"}]},
   {"op":"LLM_STEP","template":"combine_parts","schema":"answer","role":"deep"},
   {"op":"VERIFY","checker":"task"}]}

// 4. Вычисление вместо рассуждения
{"name":"program_of_thought","version":1,"origin":"builtin",
 "applies_to":{"numeric":true},
 "steps":[
   {"op":"LLM_STEP","template":"write_expression","schema":"skill_code","role":"code"},
   {"op":"COMPUTE","expr":"$last"},
   {"op":"VERIFY","checker":"task"}]}

// 5. Самосогласованность
{"name":"self_consistency_k","version":1,"origin":"builtin",
 "applies_to":{"ambiguous":true},
 "steps":[
   {"op":"VOTE","n":"$gene:reason_vote_n","agg":"majority",
    "body":[{"op":"LLM_STEP","template":"solve_direct","schema":"answer","role":"fast"}]},
   {"op":"VERIFY","checker":"task"}]}

// 6. Аналогия из графа знаний
{"name":"analogy_from_graph","version":1,"origin":"builtin",
 "applies_to":{"has_related_nodes":true},
 "steps":[
   {"op":"RETRIEVE","source":"graph","k":5},
   {"op":"LLM_STEP","template":"transfer_by_analogy","schema":"answer","role":"deep"},
   {"op":"VERIFY","checker":"task"}]}

// 7. Проверка прогнозом модели мира
{"name":"predictive_check","version":1,"origin":"builtin",
 "applies_to":{"is_decision":true},
 "steps":[
   {"op":"LLM_STEP","template":"propose_action","schema":"decision","role":"deep"},
   {"op":"PREDICT","horizon":2},
   {"op":"BRANCH","cond":"p_success_below:0.35",
    "then":[{"op":"LLM_STEP","template":"propose_alternative","schema":"decision","role":"deep"},
            {"op":"PREDICT","horizon":2}],
    "else":[]},
   {"op":"REFLECT"}]}

// 8. Отказ при недостатке данных
{"name":"abstain_on_low_confidence","version":1,"origin":"builtin",
 "applies_to":{"may_lack_data":true},
 "steps":[
   {"op":"RETRIEVE","source":"memory","k":5},
   {"op":"LLM_STEP","template":"assess_sufficiency","schema":"sufficiency","role":"fast"},
   {"op":"BRANCH","cond":"insufficient",
    "then":[{"op":"ABSTAIN","reason":"insufficient_data"}],
    "else":[{"op":"LLM_STEP","template":"solve_direct","schema":"answer","role":"fast"},
            {"op":"VERIFY","checker":"task"}]}]}
```

`$gene:<имя>` — подстановка значения гена на момент запуска (связь M5↔M6).
`$last` — результат предыдущего шага. Шаблоны промптов лежат в
`aegis/cortex/prompts/` и версионируются вместе со стратегией.

Трансформации синтезатора (шаблонный путь, без LLM) — ровно шесть, каждая

## Приложение J. Точный порядок фазы DECIDE

Порядок нормативен: он проверяется тестом и мутационным харнессом, потому что
перестановка гейтов — это дыра в безопасности, а не стилистика.

```python
def decide(ctx) -> Decision:
    # 1. Кандидаты: цели из GoalEngine + мета-цели + связанные узлы графа
    objectives = collect_objectives(ctx)                      # детерминированно, сортировано
    # 2. Доступные действия по предусловиям
    actions = ActionSpace.available(ctx)
    # 3. Оценка планов моделью мира
    plans = [planner.plan(ctx, o, actions) for o in objectives]
    # 4. Вклад ценности и политики поведения в скоринг
    for p in plans:
        p.score = (p.expected_value * g.w_ev
                   + goal_intelligence.expected_value(p.objective, ctx) * g.w_val
                   + explore_bonus(p) * g.w_exp
                   - cost_norm(p) * g.w_cost
                   - p.risk * g.w_risk
                   + policy.delta(ctx.state, p.steps[0]))
    # 5. Правила политики: suppress / prefer (SC-действия иммунны)
    plans = policy.apply_rules(ctx.state, plans)
    # 6. Приоритезация
    ordered = priority.order(plans, ctx)
    # 7. Аренда ресурсов — первый, кто получил, побеждает
    for p in ordered:
        lease = resources.reserve(p.expected_cost, p.objective, priority_of(p))
        if lease: break
    else:
        return Decision.deferred("no_resources")
    # 8. Опциональное переранжирование кортексом — ТОЛЬКО внутри ordered[:3]
    p = cortex_rerank(ordered[:3], lease) or p
    # 9. Штраф уверенности за известную историю провалов (существующее поведение)
    confidence = adjust_confidence_by_risks(ctx, p)
    # 10. Этика — последний неотменяемый гейт
    verdict = ethics.evaluate_action({...})
    if verdict.blocked:
        resources.release(lease)
        return decide_next_candidate(ctx, exclude=p)          # не более 3 попыток
    # 11. Самосохранение для модифицирующих действий
    if p.modifies_self and not self_preservation.is_modification_safe(...)[0]:
        resources.release(lease); return Decision.deferred("unsafe")
    # 12. Открытие опыта и запись прогноза — ДО исполнения
    ctx.experience_id = feedback.record_situation(...)
    ctx.prediction = world_model.make_prediction(ctx.state, p.steps[0], ctx.tick)
    return Decision(plan=p, lease=lease, confidence=confidence)
```
Инварианты, проверяемые тестами: этика вызывается **после** всех остальных и её
вердикт неотменяем; кортекс не может добавить действие вне `ordered[:3]`;
без аренды исполнения нет; прогноз и опыт открываются до действия, а не после.
