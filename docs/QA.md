# QA — процедуры, метрики качества и контроль покрытия

Документ описывает процесс контроля качества пяти ключевых когнитивных систем
AEGIS (`World Model`, `Cognitive Graph`, `Evolution Engine`, `Goal Intelligence`,
`Real-world Feedback Loop`) и то, как воспроизвести все проверки.

## 1. Уровни тестирования

| Уровень | Что проверяет | Файлы |
|---|---|---|
| Юнит-тесты | Логика каждой системы в изоляции (persistence в `tmp_path`) | `tests/test_world_model.py`, `test_cognitive_graph.py`, `test_evolution_engine.py`, `test_goal_intelligence.py`, `test_feedback_loop.py` |
| Интеграционные | 5 систем внутри реального tick-цикла `Substrate` (offline, без сети/LLM) | `tests/test_higher_systems_integration.py` |
| BDD (Gherkin) — поведение систем | Поведение пяти систем на языке спецификации | `tests/features/higher_systems.feature` + `tests/test_bdd_higher_systems.py` |
| BDD (Gherkin) — безопасность и устойчивость | Гарантии sandbox, control plane, эволюции, лога опыта, обработки ответов LLM | `tests/features/safety_and_resilience.feature` + `tests/test_bdd_safety_resilience.py` |

| Ёмкость и удержание | Поиск рисков не перечисляет всю таблицу связей; лимиты структур следуют за **измеренной** задержкой тика; вытеснение сохраняет информативное, а не частое | `tests/test_capacity_and_retention.py` |

### Правило для регрессий аудита

Тест на находку аудита обязан быть **доказуемо красным до исправления**.
Проверка выполняется прогоном нового файла тестов на коде до фикса:

```bash
git worktree add /tmp/aegis_head HEAD
cp tests/test_audit_round3.py /tmp/aegis_head/tests/
cd /tmp/aegis_head && python -m pytest tests/test_audit_round3.py -q   # ожидаем падения
git worktree remove /tmp/aegis_head --force
```

Для раунда 3 это дало **27 падений из 36** (остальные 9 — охранные тесты вида
«легитимный сценарий не должен сломаться», они зелёные в обеих версиях).

## 4. Контроль покрытия (quality gate)

Настроен в `pyproject.toml`:

```toml

source = ["aegis"]
omit = ["*/__pycache__/*"]   # больше НИЧЕГО не исключается

[tool.coverage.report]

show_missing = true
exclude_lines = ["logger.exception", "logger.warning", ...]  # обработчики ошибок
```

### Что изменилось и почему

Раньше из измерения были исключены `aegis/api/*` («покрывается интеграционно») и
`aegis/eval/sandbox.py`. Аудит раунда 3 нашёл в этих двух местах **критический
побег из sandbox с RCE** и **два мёртвых эндпоинта** (один отвечал 500 на каждый
вызов). Совпадение не случайное: неизмеряемый модуль — незащищённый модуль.
Исключения сняты, гейт поднят 85 → 90, текущее покрытие всего пакета — 92%.

Что для этого понадобилось:

| Модуль | Было | Стало | Чем |
|---|---:|---:|---|
| `eval/sandbox.py` | не измерялся | **91%** | `test_sandbox_mutation.py` (24 теста) |
| `api/server.py` | не измерялся | **75%** | `test_api_endpoints.py` (65 тестов) |

`test_api_endpoints.py` перечисляет GET-маршруты **из таблицы роутов самого
приложения**, поэтому новый эндпоинт попадает под smoke-проверку автоматически.

### Остаток непокрытого

`substrate.py` — 74%: большой async-оркестратор, непокрытое — ветки, требующие
живого LLM и многочасовых прогонов (обучение LoRA, синтез навыков). Остальные
модули ≥ 88%. Непокрытыми также остаются ветки `except → logger.warning`,
исключённые из подсчёта осознанно.

## 5. Мутационное тестирование

Инструмент: собственный харнесс `scripts/mutation_test.py` (mutmut не работает на
Windows без WSL; mutatest 3.1.0 несовместим с Python 3.11).

**Как работает:** для каждого модуля перечисляются мутанты через AST — переворот
сравнений (`<` ↔ `≥`), арифметики (`+` ↔ `−`, `*` ↔ `/`), булевых операторов
(`and` ↔ `or`), булевых констант (`True` ↔ `False`). Каждый мутант записывается в
файл, прогоняются его тесты, файл всегда восстанавливается (`finally` + резервная
копия `.mut.bak` для устойчивости к жёсткому убийству процесса). Мутант **убит**,
если тесты упали, и **выжил**, если прошли — выживший указывает на пробел в
ассертах.

**Эквивалентные мутанты** исключаются по построению: булевы флаги
`exc_info`/`ensure_ascii`/`indent`/`sort_keys` в вызовах логирования и сериализации
не меняют логику.

**Гейт:** `scripts/mutation_test.py` возвращает ненулевой код выхода, если выжил
хотя бы один (не-эквивалентный) мутант — пригодно для CI.

## 6. Изоляция тестов

Все юнит-тесты пяти систем передают `store_path=tmp_path/...`, поэтому не читают и
не пишут в рабочий каталог `data/`. Интеграционные тесты нейтрализуют сеть
(`agent_system.run_due_agents`), LLM (`llm.enabled=False`) и sandbox
(`environment.step` заглушён), обеспечивая детерминированный offline-прогон.

**Известное ограничение (реальный инцидент).** `Substrate()` читает рабочий
каталог `data/` разработчика. При написании теста R3-4 это дало ложное падение:
тест подхватил pending-кандидата эволюции из реального прогона. Правило:
**любой тест, создающий `Substrate`, обязан подменить состояние**, которое
проверяет:

```python
sub = Substrate()
sub.evolution = EvolutionEngine(store_path=tmp_path / "lineage.json")
monkeypatch.setattr(sub, "_checkpoint_path", tmp_path / "latest.json")
```

Общий фикс (фикстура, подменяющая все `*_DIR` на `tmp_path`) не сделан —
зафиксирован как долг в `docs/АУДИТ.md`.

### Нестабильные тесты: найдено и устранено

При многократном прогоне набора обнаружилось, что он падал примерно **в 2 случаях
из 5** — и падал в разных тестах. Причина оказалась общей и неочевидной:

> `HealthMonitor.check()` читает **реальные** CPU и память через `psutil`. Во время
> полного прогона (сотни подпроцессов sandbox) загрузка CPU превышает порог, health
> становится `critical`, `MetaRegulation` переходит в аварийный режим и выставляет
> `skip_learning`, а `ethics` блокирует самомодификацию. Тесты падали **на нагрузке
> машины, а не на дефекте продукта**.

Проверено воспроизведением: при подстановке `health.check() -> "critical"`
директива `skip_learning` становится `True`, и тик закономерно не запускает
обучение.

Устранено:

1. Все восемь хелперов `_make_substrate` фиксируют health как `healthy` — ровно
   тем же приёмом, которым они уже нейтрализуют сеть, LLM и sandbox.
2. Ожидания «задача ещё выполняется» переведены с `asyncio.sleep(...)` на
   `asyncio.Event`, который освобождает **сам тест**: медленный тик больше не
   может «пережить» фиктивную работу. Блокирующий тик теперь даёт чистый
   `wait_for`-таймаут вместо вердикта, зависящего от таймингов.
3. Модульная фикстура `test_api_endpoints.py` уводит хранилище навыков в
   `tmp_path`, чтобы `/api/eval` не сериализовал библиотеку, которую в этот
   момент перезаписывает другой тест.

**Результат: 17 полных прогонов подряд без единого падения.**

Правило: тест, который зависит от загрузки машины, времени или общего каталога
`data/`, считается дефектом теста. Ожидание «работа ещё идёт» выражается
событием, а не сном.

## 9. Замкнутость тестов: чем заякорено ожидаемое значение

Раунд 5 проверял набор тестов отдельным вопросом: **где мы оцениваем систему её
же собственным выходом.** Это не придирка к стилю — самозамкнутый тест зелёный
по построению и остаётся зелёным, когда система ошибается.

### Четыре формы, которые надо ловить

| Форма | Как выглядит | Почему не ловит дефект |
|---|---|---|
| Тождество | `assert f(x) == f(x)` через промежуточную функцию | Не может упасть ни при какой ошибке |
| Рефлексивность | `assert task.verify(task.expected)` | Общая ошибка нормализации в генераторе и верификаторе взаимно сокращается |
| «Второй маршрут», который первый | Тест пересчитывает ответ теми же production-функциями | Ошибка в эталонной реализации проходит дважды и совпадает |
| Самооценка улучшения | «Метрика выросла», где метрику считает проверяемый код | Генератор задач + оценщик из одного кода отменяют ошибки друг друга |

### Правило

**У каждого ожидаемого значения должен быть источник вне проверяемого кода.**
Годятся: значение, посчитанное вручную; табличное значение из учебника или
публикации; перебор; stdlib; независимая реализация; фиксированный набор с
известным ответом. Не годится: «получено запуском кода и вставлено в тест».

Тесты «run1 == run2» — законная проверка **детерминизма** и ничего больше. Они
допустимы только вместе с (а) проверкой нетривиальности состояния и (б) тестом
чувствительности, который инъецирует настоящую случайность и требует расхождения
(`test_harness_determinism.py` — образец жанра).

### Что было найдено и закрыто

- **Чистое тождество:** `reference_answer(task)` сравнивался с `task.expected`,
  а функция его же и возвращает. Заменено на сверку с ручной таблицей.
- **Рефлексивность:** `verify(expected)` теперь всюду дополнен «верификатор
  обязан сказать нет» — тем же тестом на заведомо неверный ответ.
- **Мнимый второй маршрут:** таблица проверок в `test_generators_and_splits.py`

покупаемого ресурса; лишнее процессорное время планирования уже ограничено
бюджетом латентности.

## A7. Статистика как отдельный предмет проверки

`tests/test_stats_inference.py` сверяет реализацию с аналитически известными
значениями, а не с тем, что вернул код: t-распределение при df = 1 и df = 2
имеет замкнутую форму, `t.test(1:5, 6:10)` в R даёт t = −5, df = 8, p = 0.001053,
пример Бенджамини–Хохберга 1995 года отвергает ровно две гипотезы из восьми.

Здесь же закрыт дефект, который иначе сделал бы весь контур M3 декоративным:
**Welch-тест при нулевой дисперсии в обеих выборках возвращал p = 1**. Идеально
воспроизводимый эффект — самое сильное свидетельство, какое бывает, — оказывался
«незначимым», и правило с чистым сигналом не активировалось никогда, а с шумным
активировалось. Теперь:

* майнер правил сравнивает **доли** двухвыборочным z-тестом (успехи — это
  пропорции, а не измерения; t-тест по индикаторам 0/1 делит на нулевую
  стандартную ошибку ровно там, где сигнал чист);
* испытание правила сравнивает награды через `compare_samples`: Welch там, где
  он определён, и Mann–Whitney там, где нет. Выбор делается по **форме данных**
  и всегда до того, как посчитан любой результат.

которая утечкой не является: написание навыка для `reverse` ничего не говорит об
ответе для `palindrome`.

**Сплит по хешу id, не по позиции.** Добавление задачи не пересдаёт остальные —
иначе каждый записанный ранее valid/test-скор начал бы описывать другой набор.

**Оценка — это данные.** «Применить, померить, вернуть» неверно неочевидным
образом: бенчмарк **записывает**, какие навыки сработали, поэтому измерение
варианта обучает счётчики, по которым живой solver ранжирует. Через десять
вариантов библиотека обучена экспериментом, который никто не собирался
использовать для обучения.

Приёмочный тест генераторов — approval-тест: мутанты, сдвигавшие арифметику
выбора слов, порождали идеально самосогласованные задачи, которые были просто
**другими**, и ничто больше этого не замечало.

## B2. Этап 7 — популяционная эволюция

| Критерий §M5.9 | Порог | Факт |
|---|---|---|
| Монотонность (чемпион не регрессирует) | 0 регрессий | **0** |
| `valid_test_gap` | ≤0.05 | **0.0009** |
| Прирост фитнеса за 20 поколений | ≥+15% | **+3.9% — красный** |
| Мутационный балл модулей эволюции | 0 выживших | см. ниже |

**Почему прирост красный, и почему это не дефект контура.** Фитнес — половина
от навыков, половина от поведенческого роллаута. Половина навыков ограничена
сверху четырьмя видами задач, для которых навыка нет вообще и которые никакой
ген не чинит (~0.7). Половина роллаута на 60 тиках даёт примерно 0.60–0.75.
Достижимый интервал суммарного фитнеса — около 0.65–0.73, то есть **весь
доступный размах меньше 15%**. Поиск при этом работает: за 20 поколений он
находит 2 промоушена, ни разу не регрессирует и держит `valid_test_gap` на
0.0009 при пороге 0.05.

Это ограничение **функции фитнеса**, а не поиска, и его закрывают этапы 8–9:
как только появится бенчмарк рассуждений с генераторами, у половины навыков
появится потолок, до которого действительно можно расти, и гены `reason_*`
перестанут быть инертными. До тех пор критерий честно красный.

**Геном заменён целиком.** Старый содержал `learning_rate`, `dropout`,
`attention_heads` — гиперпараметры LoRA, которых бенчмарк не касается.
Эволюция добросовестно вращала их тысячи тиков в пространстве без градиента, и
все тесты при этом проходили. Теперь каждый ген называет контур, который его
читает, а тест `test_every_delivered_gene_reaches_a_live_contour` ставит ген в
оба конца диапазона и требует, чтобы конфигурация системы изменилась.

**Три дефекта, найденные при сдаче этапа:**

| № | Дефект | Последствие |
|---|---|---|
| B1 | Оценка варианта рекурсивно запускала оценку: планировщик внутри роллаута выбирал `evolve_generation` | неограниченная рекурсия; один роллаут занимал 17.8 с вместо 3.6 с |
| B2 | Геном и `ROITracker` нормировали доли ресурсов **по-разному** | доля, записанная как 0.05, читалась как 0.09 — геном нельзя было вернуть точно, и каждый отвергнутый вариант оставлял след |
| B3 | `evolve_generation` выполнялось внутри тика | поколение — минуты работы против бюджета ACT в 20 мс; тик останавливался целиком |
| B4 | Любой длинный прогон мог запустить поколение | измерено: 137 процессов Python и набор тестов, который перестал завершаться |

B3 закрыт так же, как бенчмарк и обучение весов: действие **запускает**
поколение отсоединённой задачей, а предусловие отказывает, пока задача жива.

B4 закрыт переключателем `AEGIS_EVO_ENABLED` (по умолчанию включён). Он гейтит
**действие**, а не движок: `run_generation` вызывается напрямую всегда, и тесты
про эволюцию от этого не зависят. Набор тестов выключает его автоиспользуемой
фикстурой, а `test_evolution_is_off_in_the_suite` не даёт этому стать
молчаливым допущением.

## C2. Приёмка (`scripts/reason_bench.py`, 30 циклов, 200 held-out)

```
held-out accuracy     0.6900 -> 0.9250   (+23.5 п.п., требуется +15)
confident errors      0.3000 -> 0.0750   (-22.5 п.п., не должно расти)
лучшая одиночная встроенная стратегия   abstain_on_low_confidence  0.9100
достижимо их комбинацией                                           1.0000
слабейший класс                          arithmetic_chain (82/240)
```

**Почему потолок не занят встроенными стратегиями.** Декомпозиция и отказ
живут в **разных** встроенных стратегиях, и по отдельности ни одна не
дотягивает. Это не пробел, который надо закрыть девятой встроенной стратегией:
это место, которое нужно синтезу (M6.7). Библиотека, уже содержащая лучшую
стратегию, сделала бы M6 непроверяемым — любой измеренный прирост оказался бы
переоткрытием того, что кто-то написал руками.

Семейство `arithmetic_chain` устроено так, что одной техники не хватает: одна
задача из трёх оставляет операнд неназванным, и правильный ответ на них —
отказ. Чтобы взять семейство целиком, нужны **и** разбиение цепочки, **и**
замеченный пробел.

**Из чего складывается прирост.** Старт 0.69 — это система, которая ещё не
знает, какая стратегия какому классу подходит: выбор размазан по всем восьми.
Отбор по классам доводит до ~0.92; последние ~8 п.п. до 1.0 достижимы только
комбинацией, которой во встроенных нет. Эти 8 п.п. — задача этапа 9.

### Механизм эквивалентности

ТЗ формулирует гейт как «выживший **немутационно-эквивалентный** мутант =
провал сборки», то есть эквивалентные надо уметь фиксировать. В харнессе такой
механизм был только для косметических флагов (`exc_info`, `ensure_ascii` и
т.п.). Добавлен `KNOWN_EQUIVALENT` с тремя правилами, которые не дают ему стать
местом, куда прячут настоящие пробелы:

1. **Каждая запись несёт письменный довод**, почему наблюдаемое поведение не
   отличается. «Тест трудно написать» доводом не является.
2. **Ключ — текст строки, а не её номер.** Изменили строку — пометка перестала
   действовать, мутант вернулся. Это безопасное направление отказа.
3. **Число исключённых печатается** в каждом прогоне, поэтому «тихо простить
   больше, чем ожидает читатель» невозможно.

Шесть записей: три алгебраических (перекрёстные члены ковариации сокращаются
тождественно — проверено и символьно, и численно: 75.0 против
74.99999999999997), две «быстрый путь, полностью перекрытый нижележащей
проверкой» (обе прогнаны мутантом и дали тот же результат), одна «остаток МНК с
интерсептом равен нулю по построению, поэтому `value − mean` и `value + mean`
различаются на 2·10⁻¹⁶».

### Дефекты, найденные мутационным тестированием

Гейт нашёл три содержательных дефекта, которых не видели ни тесты, ни покрытие:

| Дефект | Последствие |
|---|---|
| **Луч символьной регрессии отсекал по BIC текущего размера** | Для `y = 2x₁ − 1.5x₂² + 3x₃` пара `(x₁, x₃)` посредственна сама по себе и является единственным путём к точному закону. Её отбрасывали, комбинацию `(x₁, x₂², x₃)` **не оценивали ни разу**, и движок возвращал `x₁³`: R² 0.97 вместо 1.0 и формула, которая просто не является законом. Исправлено отбором в луч по разнообразию наборов переменных (объединение с топом по BIC, а не замена) |
| **Комбинации не были каноническими** | Один и тот же набор термов оценивался в двух порядках, их BIC различались в последних битах, и какой победит — решал шум округления. Печатаемая формула перечисляла термы в том порядке, который случайно выиграл. Исправлено сортировкой индексов; заодно исчезла и сама конструкция со смещением |
| **`preregister` брал `getattr(hypothesis, "id", hypothesis)`** | Для словаря это возвращает сам словарь, и id плана становился строкой `"{'id': 'hyp_x'}"`. Интервенция, запущенная до постановки гипотезы в очередь, получала план, который реестр никогда не смог бы с ней сопоставить |

Первый из них — не косметика: после исправления совместная формула в приёмочном
прогоне восстанавливается **точно**
(`1.5·ev_gap + 2.502·surprise − 0.9985·brier²`) там, где раньше давала
приблизительное `0.87·exp(ev_gap) − 0.59·exp(brier)`.

## D7. Контракт метрик (Приложение G)

`tests/test_metrics_contract.py` — 61 тест, по одному на каждое имя Приложения G
плюс структурные проверки. Прогоняет **настоящий субстрат** 30 тиков и читает
телеметрию обратно.

Заглушено намеренно и узко: дорогие *производители* (бенчмарк — песочница на
задачу; среда — подпроцесс на шаг; поколение эволюции — минуты работы в другом
процессе) и то, что законно невоспроизводимо (сеть, модель, датчики хоста).
*Публикация* — код, решающий, под каким именем пишется каждое число, то есть
единственное, о чём контракт, — настоящая целиком.

Контракт двусторонний:

- каждое объявленное имя обязано появиться в телеметрии;
- **ничего не должно писаться под именем вне списка** — метрика, которую пишут,
  но не объявили, невидима для дашборда, для этого контракта и для списка
  переменных Discovery Engine: она занимает диск и никому не отвечает.

### Дефект, найденный контрактом

`EvolutionEngine()` создавался **без телеметрии** (строка 143 субстрата,
телеметрия появляется на 183 — та же схема, что для `world_model`, просто
пропущена). `publish_metrics` выходил на первой строке, и **все шесть метрик
эволюционного контура никогда не писались**: `generation`,
`champion_fitness`, `valid_test_gap`, `promotions`, `rollbacks`,
`novelty_skips`.

Ничего при этом не падало. Панель на дашборде была, ряд за ней — пустой. Это
ровно тот класс дефекта, ради которого контракт и существует: ни один тест и ни
одно покрытие его не видели, потому что код публикации исполнялся — он просто
исполнял `return`.

Дискриминация проверена: с удалённым исправлением падают ровно шесть метрик
эволюции плюс проверка полноты контуров, всё остальное зелёное.

## E7. Детерминизм: что именно гарантируется

Тест на 300 тиках проходил в изоляции и падал в полном прогоне — расхождение в
`cognitive_graph`, `emotions`, `goal_intelligence`, `memory`. Бисекция не нашла
виновного теста: падала первая половина набора, но ни одна из её четвертей по
отдельности. Это подпись **нагрузки**, а не заражения состоянием.

Причина: §3.4 *требует* выносить тяжёлую работу из тика. Бенчмарк идёт в другом
процессе, и его результат приходит на тот тик, на который успел. Под нагрузкой
он приходит на тик раньше или позже, награда за этот тик отличается, и за ней
расходятся эмоции, память, граф и ценности целей.

Два требования встречаются здесь: цикл должен быть свободен от случайности
(§3.1), а тяжёлая работа не должна быть внутри него (§3.4). Детерминирован
**цикл**, а не планировщик операционной системы. Дайджест сравнивается с
закреплённым результатом отсоединённого бенчмарка — то же решение, что уже
принято для сети и модели, и по той же причине: иначе это измерение машины.

Шаг среды при этом **не** закреплён: он выполняется синхронно внутри ACT, у
него нет тайминга, которому дрейфовать, а его закрепление изменило бы то, какие
действия выбирает планировщик, — то есть ровно то поведение, которое тест и
сравнивает.

Попутно исправлено: `_run()` не закрывал отсоединённые задачи, и они
продолжали работать во время второго прогона на общем цикле conftest.

## E9. Soak-харнесс (`scripts/soak.py`)

Прогон на сутки в сессию не помещается, поэтому он оформлен отдельным
харнессом, который проверяет все четыре утверждения §VII.5 и выносит вердикт
сам.

```bash
python scripts/soak.py                     # полные 24 часа
python scripts/soak.py --hours 2           # минимум, при котором выносится вердикт
python scripts/soak.py --interrupt-at 0.5  # убить на половине и проверить состояние
```

| Проверка | Как считается |
|---|---|
| Нет утечки памяти | RSS растёт не более чем на `--max-growth` (5%) **во второй половине** прогона |
| Ничего не осталось работать | ноль дочерних процессов и незавершённых задач после остановки |
| Все файлы состояния валидны | 78 файлов читаются настоящими загрузчиками; хранилище, загрузившееся пустым при непустом файле, — это отказ |
| Система не деградирует | темп тиков не падает вдвое от начала к концу |

Три решения, каждое из которых меняет смысл результата:

**Первая половина исключена из измерения утечки.** Каждый контур заполняет
ограниченную структуру по дороге вверх — модель мира встречает состояния, граф
набирает узлы, ряды телеметрии растут. Мерить от холодного старта значило бы
назвать этот рост утечкой. Утечка выглядит как рост, который **не прекратился**
после того, как структуры заполнились.

**Обучение весами выключено, и это единственное исключение, которое нужно
защищать.** Первый пробный прогон показал RSS 94 МБ → **4.4 ГБ** за две минуты,
когда контур сработал впервые: он скачивает модель и держит её в памяти. Это не
утечка — это загруженная модель, — но soak не отличит одно от другого, и хуже
того, четыре гигабайта законного роста спрятали бы под собой утечку любого
размера. У LoRA-контура свои тесты и своя приёмка; здесь измеряется, течёт ли
**когнитивный цикл** за сутки, а цикл — это то, что остаётся.

**Прогон короче двух часов вердикта не получает.** Пороги бессмысленны, пока
структуры не заполнились: шестиминутный пробник отрапортовал +5.5% роста, что не
говорит о сутках ничего. Такой прогон завершается статусом `inconclusive`, а не
`passed` — зелёный soak из шести минут был бы хуже, чем отсутствие soak.

Отчёт пишется в JSON по ходу прогона, поэтому машина, перезагрузившаяся на
двадцатом часу, не стоит всего измерения.
